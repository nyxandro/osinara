# Прикладные метрики Osinara для внешнего наблюдения

Эта папка описывает, что Osinara отдаёт наружу для мониторинга. Сам мониторинг живёт отдельно:
на сервере работает независимый compose-проект `monitoring-agent`, он не входит в релиз Osinara,
и контроллер деплоя его не видит и не перезапускает.

## Что здесь лежит

| Файл | Назначение |
| --- | --- |
| `sql-exporter.yaml` | Какие числа читать из представлений `monitoring_*` и как их называть |
| `compose.override.yaml` | Добавляет сервис `sql-exporter` к сборщику на этом сервере |
| `alloy-osinara-sql.alloy` | Говорит сборщику опрашивать этот сервис |

## Откуда берутся сами числа

Миграция `migrations/103_monitoring_views.sql` создаёт представления `monitoring_*`,
которые возвращают только счётчики и возрасты, и роль `osinara_metrics` с правом читать лишь их.
Права выданы на каждое представление отдельно: общий грант на схему заодно открыл бы роли и все
будущие таблицы в ней.
Представления исполняются с правами владельца, поэтому роль видит агрегаты, но ни одной строки
пользовательского содержимого: прав на `memory_items`, `telegram_ingress_updates` и остальные
таблицы у неё нет. Это проверяется тестом `agent/lib/monitoring-views-migration.integration.test.ts`.

Отдельно приложение пишет в лог строку `AGENT_SCHEDULE_TICK` после каждого успешного цикла
ежеминутных диспетчеров. Её отсутствие — единственный признак того, что планировщик встал:
сам по себе он не падает и ошибку не пишет, напоминания просто перестают приходить.

## Установка на сервере (одноразово, выполняет владелец)

1. Выдать роли пароль. В строке подключения он является частью URL, поэтому символы `@`, `:`,
   `/` и `%` в нём нужно записать в процентной кодировке; апостроф экранируется автоматически.

   ```bash
   docker compose -p osinara-production exec postgres psql -U osinara -d osinara \
     -c "ALTER ROLE osinara_metrics LOGIN PASSWORD '<из менеджера паролей>'"
   ```

2. Положить три файла из этой папки в `/opt/monitoring-agent/` рядом с `compose.yaml` сборщика,
   а `alloy-osinara-sql.alloy` — в `/opt/monitoring-agent/alloy/`.

3. Создать `/opt/monitoring-agent/osinara-metrics.env` с правами `0600` (файл читает Compose как
   `env_file`, поэтому имя фиксировано):

   ```
   OSINARA_METRICS_DSN=postgres://osinara_metrics:<пароль>@postgres:5432/osinara?sslmode=disable
   ```

4. `cd /opt/monitoring-agent && docker compose up -d`.

Проверка: `curl -s http://127.0.0.1:9399/metrics | grep osinara_` внутри сети сборщика должен
показать метрики с префиксом `osinara_`.

## Границы

Экспортёр читает базу и ничего в ней не меняет. Пароль роли не попадает в репозиторий, в аргументы
процесса и в файл конфигурации: он живёт в файле `0600` на сервере, откуда его читает окружение
контейнера, а конфигурация собирается внутри контейнера при старте. Из окружения контейнера его
по-прежнему видно тому, у кого есть доступ к Docker на сервере, поэтому смысл отдельной роли не в
сокрытии ключа, а в том, что этот ключ слабее ключа приложения: им нельзя прочитать ни одного
сообщения и ни одного воспоминания.

Восстановление базы из дампа в новый кластер требует создать роль до восстановления: роли в дамп
базы не входят, а миграция уже отмечена применённой и повторно роль не создаст. Команда приведена
в разделе «External monitoring» инструкции по деплою.
