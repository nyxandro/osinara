# Восстановление проверки памяти группы

## Инцидент 18330–18379: почему исправлений кода оказалось недостаточно

10 сентября 2026 на king-server подтверждён первый блокирующий пакет
`a96eb59c-49e4-4dd6-9318-54b50d06548a` в лейне
`ccdffe91-708e-4480-a77a-d1ba3aae0e4d` группы «Остриков пилит агентов».
Курсор — `18329`, пакет — `failed / AGENT_MEMORY_REVIEW_SOURCE_BINDING_MISSING`.
У пакета 49 источников `user` и один `telegram_bot`, sequence `18336`.
По сохранённому `eve:wrun_01M1WMZBV07RVPD9JA4QX72F3H:turn_0` фактов нет.
Прикладная и native Workflow-сессии уже удалены ретенцией.

Цепочка причин:

1. При добавлении сообщений ботов passive observer стал включать их в пакеты по 50 сообщений.
2. `bindReview` и `resolve` ещё фильтровали только `actor_kind = 'user'`. Смешанный пакет
   давал 49 строк вместо 50 и не получал подтверждённой привязки источников.
3. В прежнем runtime ошибка обработчика `turn.started` логировалась, но не останавливала модель.
   На завершении `completeBatch` обнаруживал отсутствие источников и фиксировал `failed`.
4. Commit `795ae11` от 8 сентября исправил фильтры и обязательность подготовки до модели.
   Обновление кода не изменило уже сохранённый `failed`.
5. Предыдущее восстановление `recoverUnstartedReviewBatches` работает только с
   `interactive / ambiguous / AGENT_MEMORY_REVIEW_INTERACTIVE_START_AMBIGUOUS`, без Eve binding.
   Этот пакет — `background / failed` и с binding. Он намеренно не подходит под тот ремонт.
6. `laneBlocked` прекращает подготовку и новых интерактивных, и фоновых пакетов. `claimPending`
   берёт только пакет непосредственно после курсора. Старый failed остаётся головой навсегда.

В истории commit `de351cd` эта категория прямо оставлена для ручного вмешательства. Недостающая
часть прежних работ — применение разрешённого владельцем пропуска и штатный способ его выполнить,
а не очередная смена модели или поиск причины в E5. За блокером стоят 20 pending и 8 completed
пакетов; они должны сохранить свои ID, источники и результаты.

Старый полный stream этого хода уже отсутствует. Исходная ошибка воспроизводится по составу пакета
и SQL прежней версии; первоначальный stack trace повторно прочитать невозможно.

## Штатный административный путь

После выпуска кода в production image доступен root-only CLI:

```bash
sudo docker exec -u 0 osinara-production-agent-1 \
  node .runtime/scripts/memory-review-admin.js inspect
```

`inspect` только читает: выводит группы, курсоры, первую запись на очереди, её ошибку и размер хвоста.
Он не добавляет предупреждений, не запускает Eve и не меняет аренды.

Для уже согласованного пропуска инцидента:

```bash
sudo docker exec -u 0 osinara-production-agent-1 \
  node .runtime/scripts/memory-review-admin.js skip-unbound \
  a96eb59c-49e4-4dd6-9318-54b50d06548a \
  'Владелец разрешил пропуск 18330–18379 без повторной обработки; инцидент разобран 2026-09-10'
```

Команда допустима только для головы с точным `SOURCE_BINDING_MISSING` и завершённым ходом.
Перед изменением она повторно проверяет закрытие прикладной сессии, отсутствие source set,
фактов, операций записи и evidence, а также сохранность диапазона источников.
Работающая сессия, другая ошибка, изменившиеся источники или обнаруженный результат записи
останавливают операцию без частичных изменений.

В одной транзакции пакет становится `skipped`, его диапазон и Eve binding остаются,
освобождаются ссылки удержания сообщений, курсор проходит через него и завершённых наследников,
в `audit_events` сохраняется `memory_review.operator_skipped` с причиной, прежним кодом и диапазоном.
Сами сообщения и уже сохранённые факты не удаляются. Исходное предупреждение владельцу остаётся.
Повторный или одновременный вызов не делает второй пропуск и не создаёт второй audit event.

Курсор может остановиться на следующем pending: это ожидаемо. На очередном минутном проходе
обычный dispatcher выдаёт следующий пакет. Никакого повторного send старому ходу команда не делает.

## Как считать восстановление завершённым

1. `inspect` больше не показывает исходный failed на голове; в audit ровно один согласованный skip.
2. Следующий пакет `491e2eaa-72e3-480f-a83d-e8dd06dc9ac1` начинает штатную обработку.
3. Смешанный пакет с человеком и ботом получает source set, проходит `remember` при выборе факта
   основным агентом и завершает проход. Отсутствие нового факта само по себе не ошибка: агент может
   не найти ничего долговременно полезного. Но наличие binding и завершённый проход обязательны.
4. Курсор движется и размер непроверенного хвоста уменьшается. Уже completed-пакеты не переигрываются.
5. Проверяется дальнейшая обработка новых сообщений, а не только единичное изменение статуса головы.

`failed` при нарушении происхождения данных и `ambiguous` при неясном исходе передачи в Eve по-прежнему
требуют разбора. Их нельзя автоматически объявлять успехом, безусловно пропускать или ставить заново
в очередь: это могло бы скрыть пропуски либо создать повторные факты. Новый CLI закрывает только
проверенный случай без записей; другие причины не входят в `skip-unbound`.

## Проверка изменения

Тест `memory-review-admin.integration.test.ts` использует изолированный PostgreSQL из
`compose.test.yaml`: воспроизводит сохранённый failed, его successor со смешанными источниками,
удалённую исходную сессию, административный skip, штатную привязку 50 следующих источников,
запись факта с evidence и продвижение курсора. Также проверяет одновременные вызовы,
сохранение completed-наследника, повторный terminal event и защитные отказы.
Существующий `memory-bot-sources.integration.test.ts` отдельно проходит реальный `remember`
во внешней группе для человеческого и бот-источника.

Проверено при подготовке: 15 новых тестов восстановления и 87 существующих тестов очереди,
миграций и бот-источников; typecheck; сборка runtime CLI; вызовы inspect, skip-unbound и повторного
skip-unbound на тестовой БД. Независимое read-only ревью блокирующих замечаний не выявило.

Этот документ описывает подготовленный механизм. Факт восстановления production устанавливается
по пунктам выше после выкладки и административной операции, а не по прохождению локальных тестов.
