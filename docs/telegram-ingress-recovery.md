# Восстановление обработки после сбоя PostgreSQL

## Ожидаемое поведение

Принятое Telegram-сообщение сначала сохраняется в очереди. Подготовка истории, передача в Eve,
исполнение хода и доставка результата имеют разные подтверждения. Запись сообщения в историю
сама по себе не означает, что агент уже обработал запрос.

После временного обрыва PostgreSQL:

- неподготовленное сообщение продолжает подготовку с уже записанной историей;
- сохранённый результат подготовки используется после повторной проверки текущих прав;
- незапущенная попытка отзывается под той же блокировкой строки, которую использует допуск хода;
- уже допущенное исполнение наблюдается повторно, без нового вызова задачи;
- потеря подтверждения записи завершения сверяется с фактическим состоянием БД;
- смена владельца очереди не разрешает старому наблюдателю отменять живой ход;
- отмена пользователем считается обработанным входящим запросом, а не системной ошибкой.

Аренда входящего сообщения — 60 секунд; активный обработчик продлевает её каждые 20 секунд.
Отдельный worker проверяет очередь каждые 5 секунд. Это сроки обнаружения потерянного
обработчика, а не ограничения длительности работы модели или инструмента.

## Ответы на вопросы и подтверждения

Координаты исходного вопроса (`response_*`) отделены от координат хода, исполняющего ответ
(`dispatch_*`). Ответ может законно продолжить диалог следующим ходом.

Потребление кнопки или текстового ответа сохраняется вместе с идентичностью исходного update.
Повторная передача использует существующее исключение дублей в native inbox Eve и адресуется
точной сессии. Повторный callback не подтверждает действие ещё раз. Текст отвечает на freeform-вопрос;
обычный текст рядом с кнопкой не потребляет решение, которое должно приниматься кнопкой.

Если Telegram не обновил оформление уже подтверждённого решения, это диагностируется владельцу,
а само сохранённое решение продолжает передачу. Неизвестные внешние отправки не повторяются вслепую.

## Фоновая память и расписания

Новая незапущенная фоновая попытка восстанавливается с сохранением исходного пакета сообщений.
Старая попытка теряет право на запись. Занятая блокировка или ограничение размера выборки
откладывают проверку; они не превращают восстанавливаемую попытку в окончательную ошибку.

Статус Workflow `completed` подтверждает окончание его программы, но не успех агента.
Успех проверки памяти подтверждается сохранённым терминальным событием точного хода.
Частично записанный неуспешный пакет сохраняет факты и исходные сообщения и получает диагностику
`AGENT_MEMORY_REVIEW_PARTIAL_RESULT`; он не объявляется полностью проверенным.

При исчерпании допустимых безопасных запусков расписание получает явный неуспешный статус
и уведомление владельцу, а не остаётся видимым как активное, но не исполняющееся.

## Кто получает ошибки

Системная диагностика направляется только актуальному единственному владельцу в личный Telegram.
Исходный chat ID — контекст инцидента, а не адрес доставки. Обычная личная переписка участника
не является каналом служебных ошибок.

Новые общие инциденты хранятся в `operational_incidents`. Историческая очередь уведомлений памяти
сохраняется; оба источника используют общий проверяемый owner-private транспорт.
События одного отказа дедуплицируются по операции. Неоднозначная доставка уведомления не считается
успешной и не повторяется автоматически.

## Проверка и операторское закрытие старой записи

Команды выполняются root внутри доверенного backend container:

```bash
node .runtime/scripts/telegram-ingress-admin.js inspect
node .runtime/scripts/telegram-ingress-admin.js observe UPDATE_ID "Причина проверки"
node .runtime/scripts/telegram-ingress-admin.js cancel UPDATE_ID "Причина отмены"
```

Для старой записи с подтверждённым pre-model барьером, точным `dispatch_id`, истёкшим сроком
допуска и отсутствием привязки к исполнению доступно **закрытие как прерванной**, без replay:

```bash
node .runtime/scripts/telegram-ingress-admin.js close-unbound UPDATE_ID DISPATCH_ID "Основание закрытия"
```

Команда не принимает callback/response-записи и не может закрыть уже привязанный ход.
Результат фиксируется в `telegram_ingress_recovery_events`. Исходная история остаётся в БД.

Старые неоднозначные записи без подтверждённых координат не получают выдуманных ID при миграции.
Они требуют отдельной проверки исходного исполнения.

## Допуск обновления и native worker

Для новых допусков сохраняются экземпляр backend, контейнер, PID и время старта процесса.
Reconciliation удаляет отметку только после подтверждения смерти соответствующего процесса
в этом же контейнере либо окончания точно известного native исполнения. Возраст записи
сам по себе ничего не разрешает. Проверка работает во время `draining`; в `frozen` состояние
допуска не изменяется. Старые отметки без идентичности процесса разбираются отдельно.

Закреплённый патч Graphile Worker 0.16.6 восстанавливает потерянное рабочее место после ошибки
сохранения завершения. Разблокируется только задание подтверждённо остановившегося worker;
живые соседние исполнители не затрагиваются. Повторы используют native ограниченную политику.
При её окончательном исчерпании pool переводится в отказное состояние с явной диагностикой.

Обрыв LISTEN-соединения диагностируется; чтение событий продолжает использовать уже существующую
проверку PostgreSQL по расписанию. Источником истины остаются сохранённые события.

## Проверки

- Integration-тесты с настоящим `pg_terminate_backend` и потерянным подтверждением COMMIT.
- Native Telegram e2e с отказом после сохранения решения: кнопка, freeform-ответ, следующий ход,
  отмена и однократное изменение прикладных данных.
- Native Graphile-проверка completion retry, замены погибшего worker и сохранности соседнего задания.
- `node --experimental-strip-types scripts/run-workflow-postgres-stress.ts recovery` в изолированном
  test environment: разрыв соединений Workflow, три завершённых хода и три уникальных эффекта.
- Общий production-equivalent gate из `compose.test.yaml`, чистая установка и сборка.
