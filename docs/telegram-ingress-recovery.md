# Telegram Ingress Recovery And Safe Deployment

## Внешний HTTPS На King Server

`king-server` использует отдельный Compose project `osinara-tls` с Traefik 3.7.12.
Исходники его конфигурации: `infra/traefik/compose.yaml` и `infra/traefik/dynamic.yaml`;
на сервере это `/opt/osinara/tls/compose.yaml` и `/opt/osinara/tls/traefik-dynamic.yaml`.
`OSINARA_HOSTNAME` находится в `/opt/osinara/tls/.env`. Сертификаты и ACME account хранятся
в `osinara-tls-traefik-data`, обновление сертификатов выполняет сам Traefik.
Docker socket и публичная панель управления не подключены. Единственный upstream - `edge:80`
в `osinara-production-edge-frontend`; существующий Nginx allowlist приложения сохраняется.
Это конфигурация текущего сервера, не изменение универсального installer CLI.

## Что восстанавливается

После потери обработчика новое исполнение не создаётся. Сохранённая привязка
`dispatch_id / dispatch_session_id / dispatch_turn_id / dispatch_start_index` позволяет
дочитать исходный поток Eve. Подтверждённое завершение открывает очередь; подтверждённое
прерывание закрывает отдельный запрос без его автоматического повтора. При неизвестном
результате очередь остаётся закрытой. Статус Docker healthy не доказывает доступность очереди.

Миграция 090 добавляет эти поля только как новый контракт. Старые строки, у которых известен
лишь `dispatch_started_at`, не получают выдуманную привязку. Для них требуется отдельное
сопоставление с исходным исполнением и подтверждение его остановки. Ни просьба рассказать
анекдот, ни истёкшая аренда, ни отсутствие session ID не доказывают отсутствие side effects.

## Команды администратора

Выполняются администратором внутри доверенного backend-контейнера после установки релиза.
Они не доступны модели и не добавляют публичных HTTP endpoints. В production используется
только скрипт из утверждённого image, не локальная копия исходников.

```bash
docker exec osinara-production-agent-1 node .runtime/scripts/telegram-ingress-admin.js inspect
docker exec osinara-production-agent-1 node .runtime/scripts/telegram-ingress-admin.js observe UPDATE_ID "Причина повторной проверки"
docker exec osinara-production-agent-1 node .runtime/scripts/telegram-ingress-admin.js cancel UPDATE_ID "Причина остановки исходного запроса"
```

- `inspect` показывает заблокированные записи, привязку, число проверок и длину очереди, без сообщений и секретов.
- `observe` разрешает новый ограниченный цикл наблюдения той же сессии.
- `cancel` дополнительно запрашивает нативную отмену точного хода. Ответ `accepted` недостаточен: нужен его session boundary.
- Эти операции не вызывают `send`, не стирают сообщение и не меняют карантин на completed.
- Запрос оператора сохраняется в `telegram_ingress_recovery_events`. Проверку выполняет штатный drain.
- Если binding отсутствует, команда отказывает. Нельзя вручную подставлять ID последней сессии чата или менять код ошибки ради открытия очереди.

После запроса проверять не только health, но и статус исходного update, курсор, отсутствие
карантина и обработку следующего сообщения. Отсутствие pending updates у Telegram означает
только приём webhook, не завершённый ответ агента.

## Плановое обновление

1. Скачать и проверить кандидат без остановки старого релиза.
2. Проверить handshake текущего runtime (`x-osinara-runtime-admission: 1` на закрытом drain route).
3. Установить `draining` с уникальным owner token. Новые сообщения сохраняются; новые фоновые задачи не запускаются.
4. Дождаться текущих операций. Если обнаружено ожидание ответа человека, сразу отложить обновление и вернуть обычный допуск: текст и кнопки не должны застрять за отложенными сообщениями.
5. Перейти в `frozen`, повторить проверку покоя, остановить writers, сделать backup БД и файлов.
6. Поднять кандидат, проверить health, переключить release и вернуть `ready`.

Если тишина не достигнута за 60 проверок с интервалом 5 секунд, текущая версия остаётся
работать. Обновление завершается отказом, а допуск открывается. Это не автоматическая отмена
долгой задачи ради релиза и не разрешение повторять обновление бесконечно.

При ошибке до миграции handler восстанавливает старые сервисы и допуск. После начала
неоднозначной миграции admission остаётся закрытым до проверки оператором. SIGKILL deploy-процесса
также может оставить maintenance: истечение произвольного таймера не открывает неизвестное состояние.
Для восстановления оператор должен проверить deployment ledger и фактический current release,
здоровье обеих БД и отсутствие активной попытки deploy под `/run/lock/osinara-production-deploy.lock`.
Только после этого допускается owner-token-scoped возврат maintenance в ready; нельзя очищать чужой token.

`runtime_admission_holders` сохраняет незавершённые фоновые операции независимо от жизни SQL-соединения.
После падения всего процесса запись может остаться: она блокирует deploy, но не обработку чатов.
Убирать такую запись допустимо только после проверки исходной операции и подтверждения отсутствия
её исполнителя. Автоматического удаления по возрасту нет. Scheduled/proactive application sessions
дополнительно блокируют переключение в коротком окне до создания native turn workflow.
Для HITL timeout создаётся отдельный session-bound holder до `Session.respond()`: ответ `accepted`
его не снимает. Только собственный `session.waiting` с `osinaraRuntimeHandoffIds` либо терминал
точной сессии удаляет этот барьер. Ошибка транспорта сохраняет неоднозначный handoff для проверки.
При объединении нескольких ответов pinned patch native coalescer сохраняет список holders
точных потреблённых доставок. Principal/authorization выбирает сама Eve как раньше.
Совпадение request ID с пользовательским ответом не является доказательством обработки
ещё одной synthetic timeout-доставки и не снимает её барьер.

## Первый Выпуск

Старый runtime не понимает maintenance-флаг. Новый deploy script намеренно отказывает с
`DEPLOY_ADMISSION_UNSUPPORTED`, вместо небезопасного обхода проверки.

Первую установку проводить отдельным контролируемым переключением через утверждённые CI/CD
артефакты, с проверенной остановкой старых операций, сохранением входящих Telegram updates,
миграцией 090 и синхронной установкой root-owned deploy scripts. Обычный повтор нажатия
«обновить» старым скриптом не даёт этой гарантии. После установки проверить один отложенный
деплой при активной задаче и один успешный при свободном runtime.

## Проверки В Репозитории

- SQL integration: потеря аренды и карантин, восстановление той же попытки, отказ неверной привязки, лимит проверок, audit команд, maintenance admission.
- Native Eve E2E: сохранённый binding, потеря ingress completion после ответа, дочитывание без новых model/tool calls и Telegram sends, затем следующие обращения и HITL/cancellation.
- Shell: draining/frozen с повторной проверкой, отказ при занятости, защита owner token и порядок backup.

Тесты не утверждают, что произвольный незавершённый шаг Eve никогда не повторит свой код:
это остаётся нативной семантикой Workflow и требует отдельных барьеров у внешних действий.
Восстановитель гарантирует, что сам не переиздаёт Telegram-сообщение как новый ход.
