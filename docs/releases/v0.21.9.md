# v0.21.9: восстановление Telegram и безопасное обновление

## Очередь восстанавливает наблюдение вместо повторного исполнения

Перед отправкой в Eve сохраняется отдельный ID попытки. Обязательная подготовка хода
связывает его с точными update/session/turn и исходной позицией потока до модели.
После потери обработчика приложение подключается к тому же исполнению и дочитывает
его результат, не отправляя исходное сообщение модели повторно.

Подтверждённое завершение освобождает очередь. Подтверждённое прерывание завершает отдельный
запрос с предупреждением и позволяет обработать следующие сообщения. Неизвестный результат
остаётся под защитной блокировкой. Автоматические проверки ограничены; администратор может
запросить новую проверку или отмену точного хода через runtime CLI. Запрос администратора
аудируется и сам по себе блокировку не снимает.

Старые записи без сохранённой привязки не восстанавливаются по догадкам. Они требуют отдельной
операторской проверки. Пропуск накопленной очереди не выполняется автоматически этим релизом.

## Деплой не останавливает выполняющийся запрос

Перед обновлением приложение прекращает брать новые обычные сообщения и фоновые задачи,
продолжая сохранять входящие updates. Обновление ждёт завершения текущей работы, затем
закрывает весь новый допуск и повторно проверяет состояние перед остановкой контейнеров.
Обе базы и файловые данные копируются после остановки writers.

Если за пять минут работа не завершилась, обновление откладывается, а старая версия
продолжает обслуживать пользователей. Ожидание ответа человека также откладывает обновление,
чтобы текст или кнопка не застряли за отложенными сообщениями.

Допуск фоновых операций хранится в БД и не исчезает при потере SQL-соединения.
Принятые scheduled/proactive sessions закрывают окно до появления native turn workflow.
Продолжение после HITL timeout сохраняет собственный барьер до подтверждённой границы.
Если Eve объединяет ответы, её закреплённый патч сохраняет ID именно потреблённых доставок,
не меняя выбранную авторизацию и не выводя завершение из совпадения request ID.

## Установка И Проверки

Миграция `090_telegram_ingress_recovery.sql` добавляет привязку попыток, состояние maintenance,
барьеры фоновой работы и журнал административных запросов. Версии Eve, AI SDK и остальных
зависимостей сохранены. Политики памяти и модельные настройки не меняются.

Первый переход со старого runtime требует контролируемого окна и синхронной установки
root-owned deploy scripts из canonical commit: старая версия ещё не понимает новый допуск.
Автоматического небезопасного обхода этой проверки нет. Порядок описан в
`docs/telegram-ingress-recovery.md`.

Production-equivalent Docker-проверка: 2448 тестов прошли, 3 пропущены; миграции,
проверка типов и сборка успешны. E2E использует настоящие Eve, Telegram channel и PostgreSQL,
проверяет восстановление без повторных model calls и отправок ответа, HITL, отмену и ротацию.
Включены проверки объединённых доставок и сохранности ещё не обработанной попытки.

Для текущего king-server добавлены воспроизводимые конфигурации Traefik 3.7.12.
Универсальный installer CLI этим изменением не переводится на другой TLS proxy.
