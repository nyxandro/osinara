# v0.23.0 — ограниченные серии запусков и остановка работающего расписания

Osinara получила штатное ограничение количества выполнений агентного расписания.
Просьбы вроде «присылай погоду раз в минуту, всего 10 раз» теперь можно выполнить одним
расписанием, которое самостоятельно завершается после последнего подтверждённого результата.

## Что изменилось для пользователя

### Повторить заданное количество раз

- Для повторяющегося сценария можно задать общее количество успешных выполнений.
  Планировщик хранит счёт в PostgreSQL; агенту больше не нужен файл-счётчик.
- Выполнение учитывается после подтверждённой доставки итогового сообщения в Telegram.
  Ошибка исполнения не расходует лимит, а повторная обработка того же подтверждения
  не увеличивает счёт второй раз.
- Агент получает количество уже завершённых выполнений, номер ожидаемого результата и лимит
  вместе с заданием. Эти данные можно использовать для нумерации сообщений.
- После последнего результата расписание автоматически переходит в завершённое состояние.
  Дополнительного запуска только для остановки больше не требуется.
- Интервал определяет время запуска сценария. Поиск информации, работа модели и доставка
  по-прежнему занимают время; сообщения не обязаны приходить ровно на границе минуты.

### Остановить следующие запуски во время текущего

- Пауза теперь принимается даже тогда, когда расписание уже выполняется.
  Текущее выполнение может закончить работу и отправить ответ, но новые запуски отключаются.
- Агент с правом управления расписанием может поставить свой сценарий на паузу из самого
  выполнения: например, после достижения нужной цены или появления искомого результата.
- Завершение текущего выполнения, повторная обработка событий и восстановление после
  прерванной передачи задания не отменяют принятую паузу.

### Продолжение серии и обработка ошибок

- Лимит можно увеличить или снять; уже учтённые выполнения сохраняются.
  Увеличение лимита завершённого расписания само по себе не запускает его заново — затем
  нужно явно возобновить расписание либо выполнить команду «запустить сейчас».
- Пауза, возобновление и немедленный запуск не сбрасывают счёт и не обходят достигнутый лимит.
- Возобновление после увеличения лимита выбирает новое время выполнения, а не повторяет
  уже доставленный запуск, в том числе после команды «запустить сейчас».
- Для уже выполненного однократного расписания простое «возобновить» возвращает понятное
  объяснение: нужно указать новое время либо выбрать «запустить сейчас».
- Если отправка могла состояться, но её результат неизвестен, расписание останавливается
  для проверки. Это относится и к потере связи с БД после принятия сообщения Telegram:
  сохранённое состояние доставки проверяется независимо от кода исходной ошибки.

## Инструменты и хранение данных

- `manage_agent_schedule` и `manage_external_group_schedule` поддерживают `maxRuns` в создании
  и изменении расписаний. Это общий лимит серии, включая уже учтённые выполнения;
  `maxRuns: null` снимает ограничение. У однократного расписания допустим лимит только `1`.
- Результаты управления и просмотра содержат `completedRuns`, `maxRuns` и `pauseRequested`.
  При паузе во время работы статус временно остаётся `leased`, а `pauseRequested: true`
  означает, что следующие запуски уже отключены.
- Миграция `102_agent_schedule_limits.sql` добавляет поля лимита, счётчика и запроса паузы,
  ограничения целостности и заполняет счётчик существующих расписаний по сохранённым
  завершённым запускам с подтверждениями доставки.
- Для существующих расписаний лимит автоматически не назначается. Сохранённые тексты
  сценариев, включая ранее созданные инструкции с файлом-счётчиком, не переписываются.
- Права личных, семейных и внешних групп сохраняются: новая пауза не выдаёт доступ
  к управлению чужими расписаниями или из неразрешённого режима чата.

## Проверки

- Проверены достижение лимита, повторные подтверждения, сохранение счёта после переподключения,
  одновременная пауза и доставка, ошибки исполнения, восстановление до запуска модели,
  изменение лимита, права доступа и переход со старой схемы БД.
- Отдельно воспроизведены и исправлены потеря подтверждения уже отправленного сообщения
  и различие точности времени PostgreSQL и JavaScript после немедленного запуска.
- Выполнены полный Docker-прогон проекта, дополнительные целевые проверки после независимого
  ревью, проверка типов, чистая установка зависимостей и финальная сборка с проверкой discovery.
