# v0.40.3 — мёртвый код вырезан, контроллер выкатки без мостов v0.15/v0.16

Чистка без изменений в поведении ассистента. Убран код, который никто не вызывает, мёртвый счётчик
в базе и одноразовые мосты контроллера выкатки для давно пройденных версий. Каждый пункт проверен:
вызовов нет ни в коде, ни в CI, ни в инструкциях, ни в скриптах.

Есть миграция `129`. **Переиндексация памяти не нужна.** Правила мониторинга не менялись.
**Выпуск меняет контроллер выкатки, поэтому выкатывается в две фазы:** сначала на сервер ставятся
новые модули контроллера, и только потом владелец подтверждает обновление.

## Что изменилось для пользователя

Ничего видимого. Ассистент больше не видит в инструменте завершения нити памяти вариант
`formal_goal_condition`: такой вызов всегда заканчивался ошибкой, потому что нужный итог некому было
создать.

## Для владельца и дежурного

- **Удалён код без вызовов:** репозитории `claim-evidence` и `confirmed-outcome` (итоги «из событий
  приложения», которые так и не подключили; итоги завершения нитей остаются), обёртки рабочего
  исполнителя, ручной скрипт `check-group-sandbox.ts`, форматтеры сообщений о сбое для чата (с
  13 сентября сбои уходят владельцу уведомлением) и разбор формата ошибок прежнего фреймворка в
  разборе памяти.
- **Миграция `129`** удаляет колонку `memory_threads.generation`: её только увеличивали, никто не
  читал. Функции, которые её увеличивали, по-прежнему обновляют время изменения нити — по нему нити
  сортируются по свежести.
- **Контроллер выкатки** больше не содержит мостов для переходов на v0.15.2 и v0.16.0
  (`bridge.sh`): контроллер запрещает откат, и сработать они уже не могут. Проверка прав на конфиг
  модели, которая жила внутри моста, перенесена в точку входа. CI больше не публикует в каждом
  релизе файлы `agent-model-providers.json` и `codex-subscription-model-providers.json`; конфиг
  подписки codex остаётся в репозитории — это способ вернуться на codex.
- **Фаза контроллера перед подтверждением** (`docs/production-deployment.md`): остановить
  `osinara-deploy.timer`; установить `scripts/production-deploy.sh` как
  `/opt/osinara/bin/production-deploy.sh` (`root:root 0750`) и
  `scripts/production-deploy/release.sh` (`root:root 0640`) из этого релиза; удалить
  `/opt/osinara/bin/production-deploy/bridge.sh`; сверить контрольные суммы, синтаксис, владельца и
  права; запустить таймер. Если подтвердить обновление до этой фазы, старый контроллер отработает
  с мостами, которые для 0.40.3 ничего не делают, — релиз пройдёт, но новый контроллер останется
  неустановленным.
- В инструкции деплоя описаны два вида серверов: поставленный через `osinara install` (без
  контроллера обновлений — подтверждённое обновление на нём не выкатывается) и боевой. README
  больше не обещает автоматическую выкатку на первом.
- **После выкатки проверить:** миграция `129` применена, колонки `memory_threads.generation` нет;
  следующий опрос таймера отвечает `DEPLOY_NO_APPROVED_PROPOSAL`; ассистент отвечает и записывает
  память.
