# v0.22.2: восстановление после сбоев БД и служебные ошибки только владельцу

Выпуск закрывает разрывы между сохранением входящего сообщения, запуском агента и фиксацией
результата. Временный сбой PostgreSQL больше не должен оставлять безопасно восстанавливаемый
запрос в постоянной блокировке или превращать уже записанное сообщение в пропущенную задачу.

## Восстановление Telegram

- Подготовка сообщения сохраняет отдельный результат. Наличие строки истории не подменяет
  подтверждение исполнения; восстановление использует её без дублирования.
- Перед использованием сохранённой подготовки заново проверяются актуальные права и сессия.
- Незапущенная попытка отзывается атомарно с проверкой допуска хода. Запоздалый обработчик
  старой попытки не может начать новое действие.
- Потеря связи с БД и передача аренды другому наблюдателю не отменяют живое исполнение Eve.
- Потерянное подтверждение завершения проверяется по сохранённому состоянию, без повторной задачи.
- Аренда очереди сокращена до минуты с продлением активным обработчиком; worker проверяет
  очередь каждые пять секунд. Время самой работы модели и инструментов этим не сокращается.

## Кнопки и текстовые ответы

- Исходный вопрос и исполняющий ответ ход имеют отдельные координаты: продолжение новым ходом
  больше не конфликтует с привязкой к предыдущему.
- Подтверждение сохраняется вместе с исходным update; повторная доставка в точную сессию
  использует native-дедупликацию Eve.
- Freeform-ответ сохраняет своё назначение при повторной подготовке. Обычный текст не потребляет
  решение, которое должно приниматься кнопкой.
- Ошибка оформления уже сохранённого решения не останавливает его передачу агенту.

## Ошибки получает владелец

- Тайм-ауты, ошибки ходов и сессий, расписаний и напоминаний направляются актуальному владельцу
  в личный Telegram. Исходная группа или личка участника не используются как адрес диагностики.
- Удалены прямой отправитель timeout-сообщений и исключение для публикации недоступности модели
  в группах.
- Общие инциденты сохраняются до отправки и объединяются по идентичности операции.
- Ошибка доставки служебного уведомления не должна блокировать независимые пользовательские очереди.
- Неоднозначная внешняя отправка не считается успешной и не повторяется вслепую.

## Память, расписания и обновления

- Фоновые пакеты памяти и незапущенные расписания получают безопасное восстановление передачи.
  Пропуск из-за занятой блокировки откладывает работу, а не переводит её в постоянную ошибку.
- Успех памяти определяется по событию точного хода. Технический `Workflow completed` не выдаётся
  за успешный результат агента; частичные факты и непроверенные источники сохраняются.
- Завершение напоминания можно подтвердить после обрыва БД без повторной отправки сообщения.
- При исчерпании допустимых попыток расписание получает явную диагностику владельцу.
- Допуски фоновых операций сохраняют идентичность процесса. Подтверждённо завершённые или
  оставшиеся после смерти процесса отметки сверяются автоматически, включая фазу `draining`.

## Надёжность PostgreSQL runtime

- Ошибки выданных из пула соединений обрабатываются на границе PostgreSQL. Ошибка ROLLBACK
  сохраняет первоначальную причину сбоя.
- Закреплённый патч Graphile 0.16.6 заменяет погибшего при сохранении завершения worker и
  освобождает только его подтверждённо оставшееся задание.
- Повторы служебных SQL-операций ограничены; долгий отказ не маскируется активным, но неработающим pool.
- Потеря LISTEN не лишает чтение событий существующей проверки БД по расписанию.

Версии Eve, AI SDK, PostgreSQL World и остальных зависимостей сохранены.
Миграции 094–101 добавляют метаданные восстановления, подтверждений и инцидентов; старые
неоднозначные исполнения не переигрываются автоматически.

Подробности и административные команды: [восстановление Telegram](../telegram-ingress-recovery.md).

## Проверка выпуска

В набор включены реальные разрывы PostgreSQL, потеря подтверждения COMMIT, native Telegram e2e
для кнопок и freeform-ответов, частичная память, смена наблюдателя, Graphile recovery и отсутствие
повторных эффектов в native Workflow.

Локальный production-equivalent Docker gate завершён: **2634 теста прошли**, проверка типов,
миграции и сборка успешны. Три opt-in проверки живой модели/E5 не запускались в стандартном
окружении gate. Отдельная сборка runtime CLI успешна; свежий discovery manifest содержит
ожидаемые четыре канала и четыре расписания, без ошибок и предупреждений discovery.
Независимое ревью подтвердило закрытие выявленных P1/P2.
