# Память после сравнения с Мией: что осталось сделать

Обновлено: 2026-10-17, вечер. Ветка: `feat/memory-review-selection` (от `develop` = `ebc2d70`).

Документ держит только то, что осталось сделать по плану улучшения памяти. Сделанное, но ещё не
выпущенное, превращается в одну работу — проверки после выкатки (раздел 3). У каждого пункта указан вид
работы:

- **задача** — поведение определено, можно делать;
- **проверить сначала** — проблема заявлена, но не доказана данными;
- **решение владельца** — агент не начинает без выбора владельца;
- **проверка на проде** — после выкатки, только чтение.

---

## 1. Откуда этот список

16.10.2026 владелец попросил разобрать, как устроена память у Мии — форка Osinara от Ильи Круглова
(`ilkruglov/osinara`, версия 1.8.x, отделилась от нашего кода 02.09.2026, работает на Eve), и понять,
почему её память местами нравится больше. Разбор дал 7 пунктов. 17.10 разбор пункта 2 вскрыл более
глубокую причину повторов в памяти — один человек хранился под разными именами, — и её починили вместо
пункта 2 в прежнем виде.

Разницу с Мией дают три вещи: что попадает в память, как она разложена и модель. У Мии на проде
`deepseek-flash` с глубоким рассуждением, у нас `qwen3.8-27b`. Рассуждение у qwen тоже включено: в пачке
фоновой проверки 16–17.10 из 3 445 выходных токенов 3 041 — рассуждение. Наш прошлый замер (слой 4)
показал: даже при идеальной подборке нужный факт попадает в ответ qwen только в 50% случаев.

## 3. Проверки после выкатки — проверка на проде

Четыре правки готовы и не выпущены. Проверять после выкатки, только чтением. Запросы к боевой базе —
маленькие, со `statement_timeout`. Тот же список лежит в памяти агента (`memory-release-post-checks`).

### 3.1. Привязка факта к автору сообщения — `fdff263`, миграция 134

Что сделано: фоновая проверка подписывала автора выбранного сообщения текстом («Пух (nyxandro)») вместо
ссылки на его аккаунт; такие факты не попадали в карточку, а проверка похожих записей не сравнивала их с
проверенными записями о человеке. Исправлены формулировки, сервер сам привязывает подпись с именем автора
к аккаунту, миграция 134 привязала старые записи.

Проверить:
- в `audit_events` около 1 203 строк `memory.subject_label_rebound` (125 человек);
- очередь `memory_embedding_jobs` разобралась до нуля; тревога `OsinaraMemoryIndexingStalled` могла
  сработать на время пересчёта — это ожидаемо;
- доля `AGENT_MEMORY_WRITE_SUCCEEDED` с `authorLabelBound: true` — сколько записей сервер ещё чинит сам;
  если доля высокая, читать рассуждения модели в `agent_turn_steps`;
- новые групповые записи об авторе почти все привязаны к участнику. До выкатки (фоновая проверка,
  27.09–17.10): 521 привязана, 274 подписью; неделя с 12.10 — 83 против 76;
- доля записей «не о человеке» (`subject none`, ~27–41 в неделю) резко не упала: иначе правило «автор —
  `current_author`» стало приписывать автору общие факты;
- если для внешней группы включена передача фактов в личный профиль, перепривязанные факты о членах
  семьи появятся в их профилях — предупредить владельца.

### 3.2. Имя свойства `"null"` — `99b5edd`, миграция 133

Что сделано: блок уже сохранённых записей не показывает пустое поле, имена `null`/`none`/`undefined`
получают отказ (выбор владельца), миграция сняла поле с 10 записей и вернула 3 погашенные по ошибке.

Проверить:
- `SELECT count(*) FROM memory_items_all WHERE attribute IN ('null','none','undefined')` = 0 и не растёт;
- записи `878b01e4…`, `2d2ebe97…`, `50b8e683…` активны;
- в логе нет `AGENT_TOOL_EXECUTION_FAILED` с текстом ««null» не имя свойства». Если есть — модель всё ещё
  шлёт "null", и причина была не только в блоке записей (она не доказана: сырые вызовы того времени не
  сохранились).

### 3.3. Факт из карточки раз в 20 ходов — `baf7abe`

Проверить:
- в `AGENT_MEMORY_RETRIEVAL_METRICS` поле `profileLeftOutClaims` > 0 в большинстве ходов лички,
  `profileMemoryRefs` на ход заметно меньше прежних ~8;
- доля использования фактов карточки (`memory_retrieval_shows`, источник `profile`) выше прежних 1,8%;
- в живом чате агент не вставляет факты о человеке без повода и не «забыл» его на прямых вопросах.

### 3.4. Правила отбора фактов в группах — `bf0155a`

Проверить: меньше записей «X в чате сказал, что…», нет даты сообщения в начале текста, люди названы
«Имя (username)», нет записей о шагах рабочего процесса.

## 4. Пункт 5. Постоянные поля, узкий вариант — задача

### Что не так

Проверено 17.10.2026 по данным прода:
- поле стоит у 178 из 2 581 групповой записи (~7%), в личной и семейной памяти — ни разу;
- имена полей хаотичные, английские и русские вперемешку (hobbies, sleep, `interaction_mode`, «картиночный
  раг»), почти каждое встречается один раз, поэтому замена устаревшего факта почти не срабатывает;
- широкое имя склеивает разные факты: у одного участника две разные активные записи с `interaction_mode`;
- в карточке человека имя поля не показывается (`renderClaim` в `agent/lib/profile-selection.ts`), карточка
  не упорядочена по полям;
- описания поля в `remember` (`agent/lib/tools/remember.ts`, `agent/lib/remember-contract.ts`) говорят
  «ставь для свойства, которое меняется со временем» — под это попадают и увлечения. Правила групп уже
  сужены (`bf0155a`), описания инструмента — нет;
- фоновая проверка не видит, какие поля уже заведены у людей пачки, и заводит новые имена для того же.

### Что сделать

Владелец выбрал узкий вариант: поля только для свойств с одним значением за раз. Протокол Мии «перед
записью прочитай поле и выбери: добавить или заменить» не берём (у неё 133 отказа на 420 записей).

1. Короткий список имён-образцов: «город», «место работы», «должность», «день рождения», «семейное
   положение», «как пьёт кофе» — по-русски, коротко, в именительном падеже; список не закрытый.
2. Описания поля в `remember` — на правило «одно значение за раз», с теми же примерами. Для увлечений,
   вкусов вообще и инструментов поле не ставить.
3. Карточка: показывать «город: Казань»; внутри вида записи сначала факты с полем по алфавиту поля.
4. Список полей, уже заведённых у авторов пачки (перенесён сюда из пункта 2): имена полей по каждому автору,
   ограниченно по числу; новое сведение класть в заведённое поле, новое поле — только для другого свойства.
   Блок собирать в `agent/lib/memory-review/memory-review-known-memory.ts`, выводить в
   `memory-review-prompt.ts`. После `fdff263` записи об авторах привязаны к участникам, поэтому список по
   участнику полный.
5. Возможная страховка: отказ заведомо широким именам («еда», «хобби», «увлечения», «интересы»). Решить при
   реализации.
6. Старые записи не переразмечать.

### Чем рискуем

Широкое имя всё равно проскочит и уведёт прежнюю запись в историю (она не теряется: видна в списке и
экспорте, вернётся при отмене). Имена полей добавят немного знаков в карточку — после правки «раз в 20
ходов» несущественно.

### Готово, когда

Тесты: карточка показывает имя поля и ставит факты с полем первыми; список полей содержит поля авторов
пачки и не содержит чужих; широкое имя (если делаем страховку) получает отказ с понятным кодом. После
выкатки: доля записей с полем растёт с ~7%, имена повторяются, появляются замены «город: А» → «город: Б».

## 5. Пункт 3. «Итог обсуждения» — задача, после пункта 5

### Что не так

Длинный спор или совместная работа либо не сохраняется вовсе, либо рассыпается на записи о каждом шаге.
`bf0155a` запретил записи о шагах, но целого итога взамен нет. На вопрос «к чему мы пришли по X» агенту не
из чего ответить. У Мии это событие с полем «итог обсуждения»: тема, участники, к чему пришли, что открыто;
продолжение темы заменяет прежнюю версию.

### Что сделать

1. Разрешить событию одно поле — «итог обсуждения»: сейчас поле у событий запрещено в
   `checkRememberInput` (`agent/lib/remember-contract.ts`) и `normalizeMemoryAttribute`
   (`agent/lib/memory-attribute-slot.ts`). Остальные поля у событий по-прежнему запрещены.
2. Тема — коротким устойчивым названием (`subject.kind = label`), замена версии — через существующую
   замену по слоту. Проверить, что слот события не пересекается со слотами фактов того же названия.
3. Срок жизни: обычное событие «стареет» за 30 дней (`MEMORY_RETENTION_BASE_DAYS` в
   `agent/lib/memory-forgetting.ts`); итогу нужен дольше (у Мии 60). Формула продублирована в SQL — менять оба
   места.
4. Промпт (общий блок правил групп): длинное обсуждение — одна запись-итог; если итог по теме уже есть
   среди показанных — новая версия с тем же названием темы; итог не формулировать как обещание агента.

### Чем рискуем

Модель может назвать одну тему по-разному — два итога вместо замены; помогает список полей и тем из
пункта 5, поэтому пункт 3 после него. Итог — событие, в карточку человека не попадает, только в подборку и
поиск.

### Готово, когда

Тесты: событие с полем «итог обсуждения» принимается, с другим полем — отказ; вторая версия гасит первую;
итог стареет медленнее. После выкатки: после длинного обсуждения в живой группе одна запись-итог, вопрос
«к чему пришли по X» получает ответ из неё.

## 6. Пункт 6. Сохранение в личном чате — проверить сначала

Известно: личной памяти на проде 61 запись за всё время; владелец пишет агенту в личку 41–57 сообщений в
неделю, сохраняется 2–4 записи в неделю. Фоновую проверку в личке не делаем: там агент видит каждое
сообщение сам и решение о сохранении принимает в ходе.

Неизвестно, есть ли проблема: мало записей может значить «в личке в основном поручения», а может —
«факт, сказанный мимоходом, теряется».

Что сделать:
1. Сверка только по личному чату владельца за 2–3 недели: выписать сообщения с фактами, сверить с
   сохранённым, итог — числа и примеры пропусков своими словами, без цитат.
2. Пропусков почти нет — закрыть пункт.
3. Пропуски есть — перенести в правила сохранения в ходе (`MEMORY_SELECTION_RULES`, `MEMORY_WRITE_CONTRACT` в
   `agent/lib/prompt/common-fragments.ts`) список «что искать» примерами; сократить эти правила (~9 тысяч
   знаков, у Мии 1,8); проверить описание `remember` на длину и ясность.

Готово, когда сверка сделана и пункт закрыт или превращён в задачу с числами.

## 7. Факты о других людях — проверить сначала

Найдено 17.10.2026. Сервер теперь привязывает к аккаунту только автора сообщения. Факт о другом участнике
(«Алексей посоветовал Пуху…», ответ на чужое сообщение, упоминание `@username`) по-прежнему пишется
текстовой подписью и не попадает в карточку того человека. У владельца таких записей 7 из 226 групповых с
его именем; по всей группе не посчитано.

Не привязались миграцией 134 и остаются подписями: прозвища, которых нет в сообщении («Sania (nyxandro)»),
подписи «автор — тема» («Пух (nyxandro) — Mastra», ~36), авторы без известного username (сообщения удалены
по сроку хранения, ~100), тёзки в одном чате.

Что сделать: посчитать такие записи после выкатки; проверить, хватает ли данных для привязки — в
сообщениях хранятся `reply_to_sequence_id` (кому отвечали), упоминаний `@username` отдельно нет. По итогу
решить, нужна ли привязка «тот, кому отвечали» и «упомянутый участник чата».

Готово, когда есть числа и решение: делать привязку или оставить подписи.

## 8. Найдено попутно — задачи

### 8.1. Подсказка про `manage_memory` во внешней группе

Проверено 17.10.2026: когда `remember` встречает похожую запись, ответ советует «обнови через
`manage_memory`» всем, кроме фоновой проверки (`editAvailable: source !== null && !source.isReview` в
`agent/lib/tools/remember.ts`). Во внешней группе, где право не выдано, совету нельзя последовать.

Сделать: учитывать выданные группе права при сборке подсказки (`memoryNeighbourRefusalResult` в
`agent/lib/memory-neighbour-gate.ts`). Готово, когда без выданного права подсказка не упоминает
`manage_memory` (тест).

### 8.2. Username в ленте группового хода

Проверено 17.10.2026: лента показывает имя, а username — только если имени нет
(`entry.senderDisplayName ?? entry.senderUsername` в `agent/lib/telegram-group-journal-context.ts`).
Правило «подписывай людей „Имя (username)“» поэтому в ходе группы срабатывает не всегда; фоновая проверка
username видит. У Мии это решено показом «Имя (username)» в ленте (её 1.8.35).

Сделать: показывать в ленте «Имя (username)». Правка меняет текст каждого группового хода — кэш
провайдера один раз пересоберётся. Готово, когда лента показывает оба (тест).

## 9. Решения, которые ждут владельца

### А. Запоминать, как человек общается с агентом, и порядки чата

У Мии фоновая проверка пишет в поле «общение с Мией», что человеку нравится и что раздражает, а порядки
группы — в записи о чате. Через день после запуска Мия отказалась шутить в группе, сославшись на «договор» и
«правило, которое я записала»; пришлось добавить защиты: не записывать свои обещания, записи о стиле —
подсказка по тону, а не правило. У нас стиль меняется только явной настройкой
(`manage_behavior_preference`), это решение меняет правило.

- Даёт: агент подстраивается под человека и манеру чата.
- Стоит: правка промпта проверки и карточки, плюс защиты Мии.
- Закрепляет: записи о стиле копятся и влияют на ответы; ошибочная читается как обет, пока её не удалят.

Рекомендация: после пунктов 5 и 3, сначала только в группах и только «как здесь принято», с защитами Мии;
через 2 недели проверить, нет ли отказов со ссылкой на память.

### Б. Отдельная модель для фоновой проверки

Сейчас фоновую проверку ведёт та же `qwen3.8-27b`, что и разговор (рассуждение включено). Схема настроек
модели знает две роли: основную и для картинок.

- Даёт: записи уровня Мии там, где модель не тормозит живой ответ.
- Стоит: новая роль в настройках модели; если DeepSeek — переписка групп пойдёт в DeepSeek, а не в NeuralDeep.
- Закрепляет: второго провайдера в эксплуатации и в договорённостях о данных.

Рекомендация: вернуться, если правки на qwen не дадут заметного эффекта. Перед решением прогнать слой 4
замеров (`/home/vps/osinara-eval`) с DeepSeek на той же выборке; принимает ли харнесс другую модель без
правки — не проверено.

### В. Фоновое наведение порядка по человеку

Предложено 17.10.2026 по разбору того, как это делают Zep/Graphiti, Mem0, Letta, LangMem, Hindsight и книга
«AI-агенты изнутри»: запись нового и наведение порядка — два разных процесса. Сейчас второго у нас нет:
повторы ловит только проверка похожих записей при записи (порог 0,93), а её мерило грубое — по выборке 17.10
большинство пар с похожестью ≥0,93 об одном человеке оказались разными фактами, потому что записи о человеке
начинаются с его имени. Пометка «дубль записи X» (`claim_status = 'duplicate'`) в схеме есть, но код её не
ставит: на проде 0 таких записей.

Идея: когда у человека накопилось, скажем, 10 новых записей, отдельный проход модели читает все его записи и
ставит обратимые пометки «дубль той» и «новая версия того же свойства»; текст не переписывает, ничего не
удаляет. После этого можно убрать блок из 15 последних записей в фоновой проверке (~2 тысячи токенов на вызов,
~11% стоимости пачки).

- Даёт: память чистится сама, дубли уходят из выдачи.
- Стоит: 2–4 дня и новые вызовы модели — порядка десятков проходов в день в живой группе (точно посчитать
  перед решением).
- Закрепляет: процесс, который меняет статусы записей без человека. Защита: только обратимые пометки,
  записи без имени в начале текста при сравнении, выборочная проверка глазами первые недели, откат одной
  командой, а до включения — проверка на ~100 размеченных вручную парах «дубль / не дубль» с прода.

Рекомендация: после выкатки `fdff263` и замера, сколько повторов осталось, когда записи о человеке собраны
под одним аккаунтом.

### Г. Запуск фоновой проверки по тишине (остаток пункта 2)

Пункт 2 предлагал больше контекста (40 записей и 20 сообщений вместо 15 и 5), запуск по тишине и потолок
одновременных проверок. Разбор 17.10.2026:

- потолок не нужен — проверено по коду: у каждого чата своя очередь, следующая пачка стартует только после
  предыдущей (`memory-review-dispatch-repository.ts`), а живая группа одна;
- увеличение блока записей отклонено: это подпорка, а не починка, настоящая причина повторов — разные имена
  одного человека, она исправлена в `fdff263`;
- остаётся запуск по тишине для внешних групп: 30 сообщений, или 30 минут тишины при ≥10 непрочитанных, или
  6 часов тишины.

Замер на живой группе (симуляция по реальной переписке за 14 дней, сверена с прод: 144 пачки против 142):

| | Сейчас (50 сообщений или 12 ч) | По тишине |
|---|---|---|
| Пачек за 14 дней | 144 | 283 |
| Половина сообщений разобрана за | 20 мин | 11 мин |
| 90% сообщений разобраны за | 2 ч | 55 мин |
| Входных токенов в месяц (оценка) | ~17 млн | ~20 млн |

- Даёт: память группы свежее; в тихих группах — 30 минут после разговора вместо 12 часов.
- Стоит: ~+3 млн входных токенов в месяц (оценка по модели стоимости пачки: ~12 тысяч токенов постоянной
  части на вызов, 2–5 вызовов на пачку), вдвое больше вызовов в живой группе; 1–2 дня работы.
- Закрепляет: более частые фоновые вызовы, конкурирующие с живыми ответами у провайдера.

Рекомендация: отложить. Людям выигрыш почти не виден: когда к агенту обращаются, он сам разбирает
непрочитанный хвост, и в моменте ничего не теряется. Вернуться, если после выкатки станет заметно, что память
группы запаздывает.

## 10. Что сознательно не берём

| Что | Почему |
|---|---|
| Фоновая проверка в личных чатах | В личке агент видит каждое сообщение сам; решение о сохранении — в ходе (пункт 6 вместо этого) |
| Эмбеддер BERTA вместо E5-small | Долго и дорого: свой образ, переиндексация, перенастройка порогов. Решение владельца 16.10.2026 |
| Споры между версиями записей (`unresolved_conflict`) | Убрали у себя сознательно в #358 |
| Карточки людей, о которых просто нашлась запись | Убрали в v0.45.0 по замеру: 7 333 показа, 0 использований |
| Протокол полей «добавить/заменить» | Выбран узкий вариант полей (пункт 5) |
| Больше записей в блоке фоновой проверки (40 вместо 15) | Подпорка к проверке повторов; причина повторов исправлена привязкой к аккаунту (раздел 9 Г) |
| Потолок одновременных фоновых проверок | Уже есть по устройству: одна пачка на чат за раз (раздел 9 Г) |
| Имя Мии и её правило «всегда по-русски» | Часть её характера |
| Сводка при смене сессии каждые 50 ходов | Обход ограничения Eve; наше ядро держит длинный разговор сжатием истории |

## 11. Как мерить эффект

Точка отсчёта — данные до выкатки. Повторить через 2 недели после.

| Что | Где взять | Куда должно двигаться |
|---|---|---|
| Записей в неделю по областям памяти | `memory_items` по `scope` и `created_at` | Группы — не меньше, личка — по итогам пункта 6 |
| Доля записей «X сказал, что…» и с датой в начале | `memory_items.content` | Вниз |
| Записи об авторе, привязанные к аккаунту / подписью | `memory_items.subject_participant_id` против `subject_label` + `claim_evidence` | Привязанных почти 100% |
| Записи, которые сервер привязал сам | лог `AGENT_MEMORY_WRITE_SUCCEEDED`, `authorLabelBound` | Вниз со временем |
| Доля записей «не о человеке» | `memory_items`, `subject none` | Без резкого падения |
| Записи с полем `"null"` | `memory_items.attribute` | 0 |
| Доля записей с полем, повторяемость имён | `memory_items.attribute` | Вверх (после пункта 5) |
| Предупреждения «похожая запись уже есть» на запись | лог `AGENT_MEMORY_WRITE_DEFERRED` | Без роста |
| Скрытые факты карточки, факты карточки на ход | `AGENT_MEMORY_RETRIEVAL_METRICS`: `profileLeftOutClaims`, `profileMemoryRefs` | Скрытых больше, показанных меньше |
| Доля использования показанного | `npm run memory:usage-report`, `memory_retrieval_shows` | Вверх |
