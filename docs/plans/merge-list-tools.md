# Слияние инструментов «посмотреть» и «изменить»

Статус: согласовано 04.11.2026, решения владельца — раздел 6.
Репозиторий публичный: личных данных в документе нет.

## Коротко

**Что делаем.** Семь инструментов, которые только показывают список, становятся действием `list` (или `search`,
`read`) внутри основного инструмента того же объекта. Так в проекте уже устроены `manage_skill`, `manage_api_keys`,
`manage_network_access` и `notification_settings`.

**Что увидят люди.** Ничего: агент умеет то же самое. Меняется только набор инструментов, который видит модель.

**Что получаем.**
- В личном чате владельца 45 инструментов → 38, в семейной группе 37 → 31. Модели меньше выбирать, и есть запас до
  порога 50, о котором договорились 15.10 (решение отложить подгрузку инструментов по требованию).
- Задачи и цели (следующая фича) добавят один инструмент, а не два.

**Чего не получаем.** Вес описаний почти не меняется: тексты списков переехали в действия почти целиком. Замер
04.11: личка 59 936 → 59 088 знаков (−1,4%), семья 49 061 → 48 327; у подагента +430 знаков (урезанные виды несут
описание чтения). Самое тяжёлое — `remember` (8,9 тыс.) и админка владельца (~16 тыс.) — здесь не трогается.

**За чем следить.**
1. Старая история чатов содержит вызовы удалённых имён — модель может им подражать (F1: принято, защиты не делаем).
2. Права внешних групп хранятся в базе под старыми именами — их нельзя ни потерять, ни расширить.
3. Подагент и тихий разбор групп сейчас умеют только читать — после слияния они должны видеть только чтение.
4. Боевая модель (flash) может перепутать поля разных действий одного инструмента — меряем на стенде.

## 1. Что меняется

| Было | Стало | Где выдаётся |
|---|---|---|
| `list_reminders` | `manage_reminder`, `action: "list"` | личка, семья, сценарии; во внешней группе — её собственный вариант `manage_reminder` |
| `list_agent_schedules` | `manage_agent_schedule`, `action: "list"` | личка, семья, сценарии; подагент — только `list` |
| `list_pending_family_invitations` | `manage_family_invitation`, `action: "list"` | личка владельца |
| `list_memories` | `manage_memory`, `action: "list"` | личка, семья, сценарии; подагент, тихий разбор, внешняя группа с правом — только `list` |
| `list_memory_threads`, `search_memory_threads`, `read_memory_thread` | `manage_memory_thread`, `action: "list" / "search" / "read"` | везде, где были; подагент и тихий разбор — только чтение; внешняя группа — по правам |

Итого минус 7 инструментов. Параметры удалённых инструментов переходят в действие без изменений: курсоры, лимиты,
`scope`, `history`, `status`, `query`, `threadRef`. Ответы те же.

**Не меняется:** `search_memories` (главный поиск по памяти, отдельный путь с подборкой по смыслу и периоду),
`remember`, `get_memory_source`, `export_memory`, `list_proactive_deliveries`, `list_group_history`,
`list_telegram_attachments` (семья), админка владельца.

## 2. Правила слияния

1. **Чтение внутри инструмента изменения ведёт себя как раньше:** без кнопки подтверждения, безопасно повторяется после
   сбоя. `approval` каждого инструмента для `list`/`search`/`read` отвечает «не требуется».
2. **Где раньше было только чтение, видно только чтение.** Подагент, тихий разбор групп и внешняя группа без прав на
   изменение получают тот же инструмент, но в описании и схеме только действия чтения; действие изменения сервер
   отклоняет. Так уже сделано для `manage_memory` во внешних группах (`manageMemoryPresentation`) — механизм
   обобщается на все пять инструментов.
3. **Права внешних групп не мигрируются.** В базе они остаются под прежними именами, которые становятся именами
   права на действие: `list_memories` → `manage_memory.list`, `list_memory_threads` → `manage_memory_thread.list`,
   `search_memory_threads` → `.search`, `read_memory_thread` → `.read`. Группа с правом только на поиск нитей не
   получает их список. Ни одна группа не получает и не теряет возможностей. То же для списков разрешённых инструментов
   у сценариев внешних групп (`external-agent-schedule-policy.ts`).
4. **Тексты не теряются.** Описание удалённого инструмента переезжает в его действие — в первую очередь разбор
   последнего запуска из `list_agent_schedules` (`lastRun`, `deliveredAt`, `taskOutcome`).
5. **Все упоминания старых имён обновляются:** подсказки ошибок (`model-facing-error.ts`), описания соседних
   инструментов (`remember`, `manage_memory`, `import_telegram_attachment`), промпты режимов, служебные скиллы
   `schedules`, `group-reminders`, `group-admin`, учёт показов памяти (`memory-tool-shows.ts`), подсказка про скиллы
   (`skill-offer-hint.ts`: `list` у `manage_memory` — служебный шаг, а не работа), эталонные снимки запросов в тестах,
   имена в черновике `life-matrix.md`.

## 3. Старая история чатов

После выпуска в истории активных чатов ещё есть вызовы `list_reminders` и других удалённых имён. История живёт до
сжатия или 30 дней тишины. Если модель повторит такой вызов, ядро ответит ей «такого инструмента нет — скажите, что
действие недоступно» (`tool-input-errors.ts`, `AGENT_TOOL_UNKNOWN`). Человек может услышать «не могу показать
напоминания». При прошлых удалениях (`send_workspace_file` в v0.54.0) отдельной защиты не делали; по решению F1 не
делаем и сейчас.

## 4. Как проверяем

- **Тесты рядом с кодом:** для каждого режима — какие действия видит модель; группа с частью прав не получает
  остальное; подагент читает расписания и нити, но не меняет; `list` не просит кнопку; повтор после сбоя.
- **Интеграционный прогон Docker** (`compose.test.yaml`): права внешних групп, тихий разбор, сценарии внешних групп.
- **Стенд на боевой модели** (`/home/vps/osinara-eval/tools/prompt-eval`): 40 просьб + ~8 новых на просмотр
  (напоминания, сценарии, память, нити, приглашения), по 3 прогона, до (`develop`) и после. Порог — нет новой
  устойчивой ошибки: просьба, которая на `develop` проходила, после проваливается не чаще 1 раза из 3. Плюс замер
  размера `size.mts`.
- **После выпуска:** 7 дней считать в логах `AGENT_TOOL_UNKNOWN` с удалёнными именами.

## 5. Решения агента — на проверку

1. `list_memories` уходит в `manage_memory`, а не в `search_memories`: главный поиск по памяти не трогаем, чтобы
   вызов без запроса не подменил поиск выдачей всего подряд.
2. Нити — один инструмент вместо двух (чтение + изменение): больше всего экономии, а разделение «только чтение»
   обеспечивают права (раздел 2).
3. Подагент сохраняет просмотр расписаний и нитей через урезанный вид инструмента, а не теряет его.
4. Миграции прав внешних групп нет: старые имена остаются названиями прав.
5. Вложения семейной группы (`list_telegram_attachments` + `import_telegram_attachment`) не сливаем в этот раз: это
   «найти и скачать», а не «посмотреть и изменить»; кандидат на следующий шаг.

## 6. Решения владельца (04.11.2026)

- **F1 — старые вызовы в истории чатов: ничего не делаем** (вариант Б). Модель на вызов удалённого имени получает
  обычный ответ «инструмента нет», как при прошлых удалениях. Временной подсказки нет, повтор старых историй на стенде
  не нужен.
- **F2 — чтение прода разрешено:** скиллы семьи на старые имена, ключ и конфиг боевой модели для стенда.
- **F3 — сразу не выкатываем.** Работа по инструментам продолжится, выпуск — потом, вместе со следующими изменениями.

## 9. Результат (04.11.2026)

- **Инструментов:** личка 45 → 38, семья 37 → 31, сценарий в личке 34 → 27, внешняя группа без прав 18 → 17,
  подагент 20 → 18.
- **Стенд на боевой модели** (`qwen3.8-flash-next-ru`, 52 просьбы × 3): до — 144/156, после — 144/156. В обоих прогонах
  9 провалов — просьбы про аватарки (локальный конфиг без разбора картинок), остальные 3 — единичные и разные, устойчивых
  новых ошибок нет. Все 9 новых просьб на просмотр — 3/3 и до, и после; после они идут через новые действия, вызовов
  удалённых имён ноль. Результаты: `/home/vps/osinara-eval/prompt-eval-results/457/`.
- **Скиллы семьи на проде:** из 8 активных ни один не упоминает удалённые имена. Один личный сценарий на паузе («Случайная
  погода раз в минуту») упоминает `list_agent_schedules` в тексте; данные не меняли.
- **Найдено при проверке и исправлено:** ошибка входа `manage_memory`, выброшенная на шаге подтверждения, обрывала ход;
  после слияния таких входов стало больше (одна схема на все действия). Теперь кривой вызов доходит до выполнения и
  получает обычный отказ, как у `manage_family_invitation`.
- **Независимая проверка свежим агентом** — блокеров нет. Исправлено по её замечаниям:
  - внешняя группа с правом на список памяти могла получить прежние версии записей (`history`), которых её список
    раньше не показывал, — теперь у группы этого поля нет, как и было;
  - отказ действия вне вида шёл модели как сбой с неизвестным исходом — теперь это отказ по правам
    (`AGENT_TOOL_ACTION_FORBIDDEN`), ничего не начато;
  - подагенту больше не выдаётся служебный скилл `schedules` из-за вида «только список»;
  - описания видов называют только свои действия; просмотр напоминаний не требует загрузки скилла;
  - подтверждение `manage_memory` для списка не проверяет доступ к памяти (сбой той проверки обрывал бы ход).
  Не меняли: вариант `manage_reminder` внешней группы без `replaySafe` — так было и у старого `list_reminders` группы;
  строгость к полям соседних действий — боевая модель на стенде её не задела.
- **Тесты:** модульные затронутых папок — 540 прошли (после правок по проверке); интеграционные (память, тихий разбор, приглашения, сценарии) в
  Docker — 29 файлов, 174 теста прошли; проверка типов по проекту чистая.
