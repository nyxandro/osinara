# Одна дверь в настройки владельца

Статус: согласовано 04.11.2026 (выбор владельца — вариант Б); выпущено в v0.63.0 (05.11.2026), #459 закрыт. Связано: #457 (слияние инструментов), #458 (админка не
выдаётся членам семьи). Репозиторий публичный: личных данных в документе нет.

## Коротко

**Что делаем.** Шесть инструментов администрирования владельца больше не едут в каждом ходе его личного чата. Вместо них
один маленький инструмент `owner_settings`: агент первым вызовом получает точное описание нужного раздела, вторым —
выполняет действие через тот же код, с теми же проверками и кнопками подтверждения.

**Что увидит владелец.** То же самое, что сейчас: те же карточки подтверждения, те же ответы. Перед настройкой агент
делает на один шаг больше.

**Зачем.** Описания шести инструментов — ~12 тыс. знаков в каждом ходе владельца, а нужны они несколько раз в месяц
(замер прода 04.10–04.11: ключи 10 вызовов, группы 9, остальные четыре — 0).

**Почему не «настоящая» подгрузка.** По книге из навыка `developing-ai-agents` (гл. 4 «Что делать, если инструментов
слишком много», гл. 2 «Проектирование определений инструментов»): подгрузка без пересчёта всей истории требует поддержки
API (`tool_search`/`defer_loading` у OpenAI Responses, Tool Search у Anthropic). Боевой хаб ходит по
`openai-chat-completions` — её нет, и смена набора инструментов пересчитывает весь чат (15.10 на 27b: ~48 с вместо
~2 с). Образец для такого случая там же: один инструмент-посредник, «найти → посмотреть определение → вызвать»
(`pi-mcp-adapter`, ~200 токенов). Определение приходит результатом вызова — в конец истории, кэш цел.

## Устройство

| Раздел `section` | Инструмент внутри | В сценарии владельца |
|---|---|---|
| `groups` | `manage_telegram_group` | да |
| `group_schedules` | `manage_external_group_schedule` | да |
| `invitations` | `manage_family_invitation` | да |
| `group_profiles` | `manage_profile_projection` | да |
| `network` | `manage_network_access` | нет, как и сейчас |
| `api_keys` | `manage_api_keys` | нет, как и сейчас |

- `{"section":"groups"}` — описание раздела: текст и схема параметров инструмента внутри, ровно как их получила бы
  модель, плюс соответствие имён внутренних инструментов разделам (их описания ссылаются друг на друга по именам).
  Ничего не меняет, подтверждения не просит.
- `{"section":"groups","call":{...}}` — вызов. `call` проверяется схемой инструмента внутри (раньше это делал провайдер
  модели); ошибка возвращается модели как ошибка входа (`AGENT_OWNER_SETTINGS_INPUT_INVALID`, можно исправить и
  повторить) с перечнем полей и подсказкой взять описание раздела. Дальше — подтверждение и выполнение самого
  инструмента, без изменений; отказ входа самого раздела переписывается под форму вызова через «дверь».
- Инструмент, который сам сверяется с записью подтверждения (перенос фактов в профили), сверяется с вызовом «двери» —
  именно его подтвердил владелец (`withConfirmedCall`).
- Вход «двери» описан готовой JSON-схемой: из zod AI SDK запретил бы любые поля внутри `call`.
- Карточка подтверждения показывает вызов внутри «двери» — те же тексты, что сейчас. Учёт подтверждения хранит исходный
  вызов «двери».
- «Дверь» есть только в личном чате владельца (#458). Подагенту и членам семьи она не выдаётся.
- Служебные скиллы `group-admin` и `api-keys` выдаются там, где есть «дверь»; их тексты, блок «Администрирование» в
  инструкциях лички и подсказки ошибок называют вызовы через неё.

## Решения агента — на проверку

1. Повтор после сбоя: «дверь» не помечена безопасной для повтора, потому что два инструмента внутри (`groups`,
   `api_keys`) такими не помечены. Вызов, прерванный падением процесса, вернётся модели как «исход неизвестен», а не
   выполнится второй раз. Для четырёх других разделов это чуть хуже, чем сейчас; падение посреди вызова настройки редко.
2. Замеры вызовов (`AGENT_TOOL_CALL_METRICS`) пишутся под именем `owner_settings`; раздел виден по коду ошибки инструмента
   внутри. Отдельной строки журнала не добавляем.
3. Скилл `api-keys` выдаётся и в сценарии владельца, где раздела `api_keys` нет: скиллы привязаны к имени инструмента.
   Лишний пункт в каталоге, без вреда.

## Проверка

- Тесты рядом с кодом: описание раздела без подтверждения; вызов с неверным `call` не доходит до инструмента и не
  обрывает ход; подтверждение и выполнение — инструмента внутри; раздела нет — отказ; сценарий без `network`/`api_keys`;
  карточка подтверждения и учёт.
- Стенд на боевой модели: просьбы владельца про группы, приглашения, сеть, сценарии групп, `/status` — до и после.
- Вес: личка владельца 38 → 33 инструмента, ~59 → ~48 тыс. знаков (замер ниже).

- **Вес:** личка владельца 38 → 33 инструмента, 59 098 → 48 432 знака (−18%). Сама «дверь» — 1 394 знака (оценивал
  ~600). Чат члена семьи (#458): 32 инструмента, 47 038 знаков.
- **Стенд на боевой модели** (12 просьб владельца × 3: `/status`, новый контекст группы, голосовые в группе, скилл группе,
  сценарий группы, приглашение, список кандидатов, сетевой доступ, тихие часы, напоминание, сценарии, память): до «двери»
  35/36, после — 34/36. Промахи единичные: в одном прогоне агент сначала проверил адрес `curl` перед запросом сетевого
  доступа, в другом — `bash date` для дня недели (известная привычка flash). Все 38 вызовов через «дверь» проходят схему
  своих инструментов. Контракт раздела агент читает, когда ему не хватает текста скилла; в остальных случаях сразу вызывает.
- **Тесты:** модульные затронутых папок — 937 прошли; проверка типов по проекту чистая.

### Независимая проверка свежим агентом

- **Блокер, исправлен:** включение и выключение переноса фактов в профили через «дверь» после кнопки всегда отказывало —
  инструмент искал подтверждение под своим именем, а оно записано под именем «двери». Теперь сверка идёт с вызовом
  «двери»; путь проходит сквозной тест «подтверждение исполняется один раз при двойном нажатии после перезапуска».
- **Серьёзно, исправлено:** ошибка входа «двери» шла модели как «сбой, не повторяй» и в лог уровня error — теперь
  ошибка входа, которую можно исправить; закрытый раздел — отказ по правам.
- **Исправлено:** схема `call` уходила модели как «только пустой объект»; отказ раздела не подсказывал форму вызова
  через «дверь»; чтение описания раздела считалось рабочим шагом для подсказки «сохранить как скилл»; текст скилла
  `api-keys`; тесты на `recovery_owner`, подтверждение через «дверь», карточки групп и профилей.
- **Оставлено:** карточка показывает `call`, как прислала модель, а выполнение идёт по разобранному схемой входу; сейчас
  они совпадают (у схем разделов нет значений по умолчанию).

### Прогоны после исправлений

- Docker: оба сквозных теста (9) прошли; интеграционные подтверждений, памяти, тихого разбора, приглашений и сценариев —

- Стенд на окончательном варианте (12 просьб × 3): 34/36, все 38 вызовов через «дверь» проходят схемы. Промахи: старый

  песочница без доступа до адреса не достучится.
