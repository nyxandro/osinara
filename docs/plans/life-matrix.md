# Нити и проактивность: спецификация

Статус: черновик к согласованию, 27.10.2026, редакция 4.3. Код по этой спецификации не менялся.
Репозиторий публичный: личных данных в документе нет, все примеры обобщены.

**История редакций:**
- **1** — «матрица жизненной активности» с весами на узлах.
- **2** — исправления после независимой проверки по коду.
- **3** — решения владельца: инициативы включены по умолчанию, лимитов на количество нет.
- **4** — решение владельца отказаться от отдельной матрицы: основой и для проактивности, и для «проектов» становятся
  нити памяти. Чем редакция 4 отличается от 3 — в разделе 15.
- **4.1** — семейные нити видны и ведутся из личных чатов членов семьи (замечание владельца).
- **4.2** — «проекты» убираются, их роль берут на себя нити (решение владельца).
- **4.3** — поле нити «о ком» больше не ограничивает, какие факты кладутся в нить. Оно становится необязательным «чья
  линия» и различает одноимённые нити разных людей по проверенному участнику, а не по имени.

## 1. Зачем

Агент должен вести длящиеся линии жизни человека и сам замечать, когда может помочь, без заранее расписанных
сценариев. Что значит «вести линию»:
- помнить, на каком этапе дело;
- что решили;
- какие сроки;
- какие документы относятся к делу.

Сейчас это нужно для личных и семейных чатов. Позже появится режим рабочих чатов: там нить работает как журнал
проекта, где собраны решения, сроки, задачи и документы.

Примеры, на которых проверяется замысел:

| Линия | Что агент ведёт | Что может сделать сам |
|---|---|---|
| повторная покупка | даты покупок | «скоро пора снова — помочь заказать?» |
| поездка | маршрут, даты, открытые вопросы, билеты | «до вылета неделя, а жильё не решено» |
| прогресс (вес, сон, накопления) | замеры и цель | «неделю нет замера», «до цели N при нынешнем темпе — к такой-то дате» |
| сериалы, книги | что смотрел или читал, оценки, как менялись вкусы | советует без повторов; позже — сам, когда вышло подходящее |
| хобби | хроника, цели, ссылки | напоминает о цели, если у неё есть срок |
| рабочая тема | решения, сроки, задачи, документы | «срок завтра, а вопрос не закрыт»; находит нужный документ по памяти |
| интерес к новинкам | когда человек спрашивал | позже — сам приносит крупные новинки |

**«Работает» значит:**
1. Агент сам заводит нити и ведёт их по ходу разговора.
2. Большинство инициатив человек отмечает полезными.
3. Когда сказать нечего, агент молчит.
4. Ни одна инициатива не раскрывает чужое личное и не тратит деньги без подтверждения.

## 2. Решения владельца (27.10.2026)

1. Отдельной «матрицы» нет. Основа и для проактивности, и для «проектов» — **нити памяти**. Слово «проект» агенту
   не нужно.
2. **Нить — хроника любой стороны жизни**: хобби, здоровье, вкусы, поездки, покупки, работа. Это не рабочий
   планировщик и не трекер задач.
3. **Инициативы включены по умолчанию** у каждого члена семьи. Каждый может выключить их для себя словами.
4. **Лимитов на число инициатив нет**: сколько поводов созрело и прошло проверку, столько и уходит.
5. **В личке и семье фонового разбора памяти нет**: агент видит каждое сообщение, а наполнение чинится промптами. Тихий
   обход остаётся только в групповых чатах — он не даёт потерять сообщения между редкими вызовами агента. Его
   доработка под нити будет вместе с режимом рабочих чатов.
6. **Устройство нити закладывается сразу так**, чтобы оно подошло для будущих рабочих чатов: решения, сроки, задачи,
   документы.
7. **Семейные нити доступны в личных чатах** каждого члена семьи: их видно, и их можно вести оттуда.
8. **«Проекты» памяти убираются.** Их роль целиком берут на себя нити (раздел 9).

Учитываются и прежние решения:
- **21.10:** миграции, которые переразмечают сохранённые записи памяти, не делаются. Существующие записи не
  трогаем. Удаление «проектов» (п. 8) — отдельное решение владельца. Это не исправление записей по суждению
  агента, а снятие дублирующей связи: смысл ни одной записи не меняется.
- **21.09:** слой документов в памяти не делаем. Запись-указатель на документ (раздел 5.6) это решение уточняет — ждёт
  подтверждения владельца.

## 3. Принципы

1. **Память — источник правды.**
   - Факт памяти — что было сказано (текст, ищется поиском).
   - Запись нити — как это меняет линию: дата, состояние, срок, замер, документ.
2. **Сохраняет только основной агент** — `remember` и инструмент нитей. Отдельных проходов модели для извлечения
   нет.
3. **Модель называет, код считает.** Ключи и состояния пишет модель. Даты, ритмы, динамику и поводы считает код —
   только по полям, не разбирая текст.
4. **Решение «писать ли человеку» исполняет backend**, а не модель.
5. **Каждая инициатива опирается на нить** и называет причину.
6. **Сбой ведёт к тишине:** нет данных или повода — нет сообщения.
7. **Подготовка инициативы только читает.** Набор её инструментов задаёт код. Покупки и сообщения другим людям — только
   из разговора, через существующие подтверждения.
8. **Области изолированы, а семейное видно всей семье.**
   - Личную нить видит только её хозяин.
   - Семейную — все члены семьи: в семейной группе и каждый в своём личном чате.
   - Групповую — только эта группа.
9. **Без новых механизмов ядра:** ни второго цикла агента, ни транспорта, ни авторизации, ни подтверждений (AGENTS.md).
10. **Сейчас закладываем то, что потом пришлось бы переделывать в сохранённых данных.** Остальное добавляется позже,
    отдельными изменениями, не трогающими данные.
11. **Параметры поведения — константы в коде**, не `.env`.

## 4. Как нити устроены сейчас

Проверено по коду и боевой базе 27.10.

### 4.1. Таблицы

**`memory_threads` — нить:**
- `thread_ref` — номер, по которому на нить ссылается агент;
- `scope` и ключ области;
- «о ком» нить — один из двух видов:
  - **про человека** (`subject_user_id` / `subject_participant_id`);
  - **про тему** (`memory_project_id` — «проект»);
- `parent_thread_id` — родительская нить;
- `title` — до 120 символов;
- `purpose` — до 500;
- `status` — только `active` или `completed`;
- смысловой отпечаток названия.

**`memory_thread_entries` — записи нити:**
- `role` — цель, ограничение, способ, решение, эпизод, итог, урок, открытый вопрос;
- `occurred_at`;
- ссылка на источник. Ограничение базы требует ровно один источник: факт памяти или подтверждённый итог
  (`num_nonnulls(source_claim_id, source_outcome_id) = 1`).

**`memory_items_all` — факты:** текст, вид, о ком, дата события `occurred_on`, слот свойства, уверенность,
чувствительность. Кто сказал и когда — в `claim_evidence`.

**«Проекты» (`memory_projects`)** — пара к нити-теме, один к одному. Других задач у проекта нет, кроме двух: быть
«паспортом» такой нити и отделять слоты свойств одной темы от другой.

### 4.2. Как агент заполняет нить

- **Создать нить или добавить запись можно только вместе с новым фактом**, одним вызовом `remember` с блоком
  `thread`: `create` или `attach`, плюс роль.
- **Инструмент `manage_memory_thread`** умеет только «завершить» (по словам человека или подтверждённому итогу) и
  «вернуть в работу».
- **Защита от дублей:** нить со слишком похожим названием создать нельзя (порог похожести 0,92). При точном совпадении
  названия запись прикрепляется к существующей нити.
- **Совместимость записи с нитью.** Нить «про человека» принимает только факты об этом человеке, нить «про тему» —
  только факты ни о ком (`memory-thread-write.ts`, `requireCompatibleIdentity`). В личной памяти нить «про тему»
  запрещена (`remember-contract.ts`).
- **Дата записи нити** — время сообщения. Дата события из факта не используется.
- **Уведомление «начата новая нить»** показывается только в личке.
- **Из какого чата какая память видна** (`conversation-environment.ts`):
  - личный чат — личная и семейная;
  - семейная группа — только семейная;
  - внешняя группа — только своя.

  Чтение нитей это учитывает: семейные нити видны и в личке. Писать в семейную память из лички сейчас можно только
  по прямой просьбе сделать факт общим (`mode-instructions.ts`).

### 4.3. Что агент видит

- Автоматически — не больше 2 нитей, подобранных по совпадению с темой сообщения.
- По каждой — сводка, которую собирает код без модели: записи по ролям, до 20 пунктов и 6000 символов, плюс 3
  последних эпизода.
- Целиком нить читается инструментом `read_memory_thread`: заменённые записи приходят там без пометки.

### 4.4. Документы сейчас

Присланный в чат файл сохраняется надолго в рабочей папке области: `inbox/<номер сообщения>/<имя>`, постоянный том.
Агент может найти его поиском по папке и прочитать встроенными навыками (PDF, Word, Excel). Но связи файла с нитью
или с памятью нет.

### 4.5. Как это используется

- В личке — 3 нити и 12 записей.
- В семье — ни одной.
- В группах — 57 нитей. Из них 41 нить-тема, и все они в одной внешней группе. У 30 из этих 41 ровно одна запись.
- Записей проектов 77, и все уже лежат в своих нитях.

### 4.6. Что из этого следует

1. **Даты нельзя посчитать.** Даты есть только словами в тексте, а дата записи — время сообщения.
2. **У пунктов нет состояния.** Задача «продлить» записывается как «ограничение», без «сделано / не сделано».
3. **Правило «о ком нить» не пускает нужные факты.** Факт о другом человеке в контексте вашей линии, или факт о рабочей
   теме в личке, положить в нить нельзя.
4. **Положить в нить можно только новый факт памяти.** Свои предложения агента, реакции и документы — нельзя.
5. **«Проекты» дублируют нити один к одному.**
6. **В личке нити почти не заводятся, в группах заводятся на разовые вещи.**

## 5. Новое устройство нити

**Термины.** В этом документе две разные вещи:
- **факт** — запись памяти (`memory_items_all`): текст и его свойства, в том числе «о ком» — о вас, о другом
  проверенном человеке, о ком-то по имени или ни о ком. Это поле у фактов есть и сейчас, его не меняем;
- **запись нити** — строка нити (`memory_thread_entries`): она либо ссылается на факт, либо хранит заметку (предложение
  агента, нажатие кнопки), и несёт поля нити — ключ, состояние, даты, замер, файл.

Нить собирает записи; «о ком» — свойство факта, а не нити.

### 5.1. Чья нить и где она видна

Нить принадлежит **области памяти**: человеку (личная), семье или группе. Это уже определяют `scope` и ключ
области. **Область — не чат.** Семейная нить живёт в семейной памяти, и её видно везде, где видна семейная память.

| Нить | Где видна и откуда её можно вести |
|---|---|
| личная | только из личного чата её хозяина |
| семейная | из семейной группы и из личного чата каждого члена семьи |
| групповая | только из этой группы |

Пример: семейную поездку начали обсуждать в семейной группе, а продолжаете в личке. Это одна и та же нить: в личке
агент видит её сводку и добавляет в неё записи.

**Какие записи можно положить в нить** — только те, которые видят все, кто видит нить:
- **в личную** — личные записи её хозяина и семейные записи: хозяин и так видит семейную память;
- **в семейную** — только семейные записи. Личная запись в семейной нити раскрыла бы личное всей семье;
- **в групповую** — только записи этой группы.

Что ещё меняется:
- у каждого факта остаётся его собственное «о ком», как и сейчас: от этого зависит, в чью карточку «про человека»
  он попадёт;
- проверка совместимости записи с нитью сводится к правилу выше, а вид «про человека / про тему» исчезает;
- **поле нити «о ком» меняет смысл: оно становится необязательным «чья линия».**

  | Что поле делает сейчас | Как станет |
  |---|---|
  | пускает в нить только факты об этом человеке | **больше не ограничивает:** в нить кладутся любые видимые факты (правило выше) |
  | различает одноимённые нити разных людей в одной группе («Учёба» одного и «Учёба» другого) | **остаётся.** Различает по проверенному участнику, то есть по его Telegram-аккаунту, а не по имени: два Алексея в одном чате — два разных участника и две разные нити «Учёба». Защита от дублей сравнивает название только внутри одной «чьей линии» |
  | передаёт «о ком» итогу, когда нить завершают | остаётся как есть |

  Когда поле заполняется:
  - **нить — линия одного человека** («учёба», «похудение», «проект участника») — указывается этот человек. Модель
    передаёт его тем же способом, что и «о ком» у факта: автор сообщения или проверенный участник из контекста хода,
    а не имя текстом;
  - **общая тема** («релиз», «поездка семьи») — поле пустое;
  - **личная нить** — поле не нужно: хозяин и так известен по области.

  О ком нить, если это человек, не названный в чате (например, клиент), различает только название;
- «проекты» убираются, их роль берёт на себя нить (раздел 9).

**Как вести семейную нить из лички.** Нынешнее правило «в семейную память из лички — только по прямой просьбе
сделать общим» для семейных нитей меняется:
- человек в личке продолжает семейную линию — даты, брони, решения, документы по общему делу → запись идёт в
  семейную память и в семейную нить;
- агент коротко сообщает: «добавил в семейную нить «…» — её видит семья». Это можно отменить: отмена записи уже есть;
- **личное остаётся личным, даже если сказано по этой теме:** мнения о родных, чувства, то, что человек не говорил бы
  при семье. В семейную нить это не попадает;
- если неясно, общее это или личное, агент спрашивает.

Автоматически это или только по просьбе — вопрос 4 в разделе 14.

### 5.2. Нить — хроника, формы нет

Любая нить — это записи с датами и история изменений. Отдельного «типа» или «формы» у нити нет. Что считать, код
видит по самим записям:
- есть числа — динамика;
- есть регулярные даты — ритм;
- есть сроки — сроки;
- есть будущая дата и открытые вопросы — план.

### 5.3. Запись нити: одна форма, необязательные поля

| Поле | Зачем | Пример |
|---|---|---|
| `role` | как сейчас, восемь ролей; старые записи не переделываются | `open_loop` |
| `source_kind` | откуда запись: факт, итог, ход агента, нажатие кнопки | `fact` |
| `key` + нормализованная копия | что запись обновляет | «жильё на месте», «вес», «Сериал А», «БД проекта» |
| `state` | для расчётов: `open`, `done`, `dropped` | `open` |
| `label` | подпись для человека | «не решено», «досмотрела», «предложено 3 варианта» |
| `event_on` | дата события | 2026-11-03 |
| `value`, `unit` | замер | 83, «кг» |
| `due_on` | срок | 2026-11-01 |
| `file_path`, `file_sha256` | документ в рабочей папке области | `inbox/…/ticket.pdf` |
| `note` | текст записи, если это не факт памяти | «27.10 предложил: …» |

**Правило одно: последняя запись по ключу — текущее состояние, остальные — история.** Все случаи — это разные
наборы полей одной записи:

| Что | Поля |
|---|---|
| статус сериала или книги | ключ + состояние + подпись |
| задача или этап со сроком | ключ + состояние + срок |
| решение, которое потом поменяли | ключ: новая запись заменяет прежнее решение, история остаётся |
| замер | ключ + число + единица + дата |
| открытый вопрос и его закрытие | ключ + `open` → `done` |
| событие («заказал», «созвонились») | ключ + дата события |
| документ | факт с кратким содержанием + файл |
| «агент предложил» | ключ + подпись + `note` (источник — ход агента) |
| реакция («ещё есть», пауза) | ключ или вся нить + подпись (источник — нажатие) |

Запись без ключа — просто факт в хронике. Это нормально: «жил там полгода» никакого состояния не обновляет.

Слоты свойств остаются только для свойств человека (город, место работы). Для статусов в нитях они больше не
нужны.

### 5.4. Источники записей

`source_kind`:
- `fact` — ссылка на факт памяти;
- `outcome` — подтверждённый итог;
- `agent` — ход агента;
- `press` — нажатие кнопки.

Ограничение базы «ровно один источник» заменяется проверкой по виду источника. У каждой записи видно, кто, когда и
откуда её создал. Записи `agent` и `press` не являются фактами памяти и поиском памяти не ищутся — они видны в нити.

### 5.5. Ключи

Главный риск схемы — разъехавшиеся ключи: «вес» и «Вес утром» превратили бы одну историю в две. Защита:
- сводка нити показывает список существующих ключей, а правило велит брать ключ из него дословно;
- код хранит нормализованную копию: регистр, пробелы, «ё»;
- новый ключ, слишком похожий на существующий в той же нити, код отклоняет с подсказкой, как это уже сделано для
  похожих названий нитей. Агент либо берёт существующий ключ, либо подтверждает, что это другое.

### 5.6. Документы

Документ — это факт памяти с кратким содержанием плюс запись нити с файлом:
- **факт** — что это, о чём, ключевое, кто и когда прислал. Он ищется поиском памяти;
- **запись нити** — `file_path` (файл уже лежит в рабочей папке области) и `file_sha256`; ключ — если документ
  относится к конкретному пункту, например «билет» к «вылету».

**Как это работает:**
1. Пришёл документ по линии → агент читает его встроенным навыком → сохраняет факт и запись одним вызовом.
2. Вопрос о документе → агент находит его по памяти или по сводке нити → открывает файл за деталями.
3. Файл изменился или удалён (не совпала контрольная сумма или файла нет) → агент так и говорит.
4. Новая версия документа — новая запись с тем же ключом, старая уходит в историю.

**Границы:**
- Нет разбора документа на части, нет индекса по содержимому, нет фоновой обработки. Найти документ можно только по
  его краткому содержанию, детали — по самому файлу.
- Документ с чувствительными данными (паспорт, договор, медицина): факт помечается чувствительным, номера и реквизиты
  в краткое содержание не попадают.
- Текст файла — недоверенные данные: инструкции из файла в краткое содержание не переносятся.
- Для длинного документа краткое содержание честно говорит, что прочитано («первые 30 страниц»).
- Удалить запись можно словами. Удаление самого файла — только с подтверждения, как уже устроено.

### 5.7. Когда заводить нить

**Критерий: у темы будет продолжение.**
- **Нить:** «худею», «подсела на такие-то сериалы», «начал учить фотографию», «планирую поездку», «взял новый рабочий
  проект», «покупаю это регулярно».
- **Факт без нити:** «сходил вчера в кино», «был на встрече».
- **Как отразится:** в личке нитей станет больше (сейчас их почти нет); в группах станет меньше одноразовых.
- **Вложенные нити уже поддерживаются.** Например, «Работа» → тема → выпуск.

### 5.8. Сводка нити в разговоре

Её собирает тот же генератор без модели, с теми же ограничениями: 2 нити, до 20 пунктов. Порядок новый:
1. просроченное и ближайшие сроки;
2. открытые пункты;
3. текущее состояние по ключам, с последним замером и его динамикой;
4. последние события;
5. документы (название, дата);
6. список ключей нити.

### 5.9. Чтение нити с отбором

`read_memory_thread` получает необязательные фильтры:
- по ключу;
- по состоянию;
- по периоду;
- только документы;
- только текущее состояние (последняя запись по каждому ключу).

Записи отдаются по дате события и с пометкой «действующая / заменённая».

### 5.10. Показ, правка, слияние, удаление

- **Показ.** «Какие у меня нити», «что по нити X» — существующими инструментами списка, поиска и чтения.
- **Слияние.** Если агент завёл дубль, он сливает две нити новым действием `merge`: записи переносятся, название
  остаётся у одной.
- **«Забудь» и выгрузка** покрывают записи нитей.

### 5.11. Как агент заполняет: контракты

Факт и запись нити — одним вызовом `remember`. Блок `thread` получает поле `entry`:

```json
{
  "content": "Вылет 3 ноября, билет куплен",
  "kind": "episode", "occurredOn": "2026-10-27", "basis": "agent_inferred",
  "scope": "personal", "sensitivity": "normal", "subject": { "kind": "current_author" },
  "thread": { "action": "attach", "threadRef": "thread_…", "role": "decision",
              "entry": { "key": "вылет", "eventOn": "2026-11-03", "state": "done", "label": "билет куплен" } }
}
```

Другие примеры поля `entry`:
- замер: `"entry": {"key": "вес", "value": 83, "unit": "кг", "eventOn": "2026-10-27"}`;
- документ: `"entry": {"key": "вылет", "label": "билет", "file": "inbox/…/ticket.pdf"}`.

Запись, которая не является фактом, идёт через `manage_memory_thread` с новым действием `add_entry`. Ещё одно новое
действие — `merge`.

```json
{ "action": "add_entry", "threadRef": "thread_…",
  "entry": { "key": "жильё на месте", "state": "open", "label": "предложено 3 варианта", "note": "27.10 предложил: …" } }
```

Нажатия кнопок пишет backend сам (`source_kind = press`).

### 5.12. Что увидит агент: пример сводки

```
Нить «Поездка» — активна
Сроки:     вылет — 03.11 (через 7 дней); продлить карты — до 01.11
Открыто:   жильё на месте — не решено (предложено 3 варианта, 27.10); карты — нужно продлить
Текущее:   маршрут — …; цель поездки — …
Документы: билет (inbox/…/ticket.pdf, 27.10)
Ключи:     маршрут, цель поездки, вылет, жильё на месте, карты
```

## 6. Этап 1: промпты

Промпты модели английские (с v0.44.0), содержимое записей — русское. Формулировки проверяются боевой моделью и
живым чатом (AGENTS.md).

### 6.1. Что сохранять: дополнение к `MEMORY_SELECTION_RULES`

Первый абзац с широким перечнем остаётся: в коде прямо записано, что закрытый список учит модель пропускать. После
перечня добавляется:

```text
In particular, look inside questions and requests: the request itself is not a fact, but it often carries one.
Watch for a taste (what they like or reject, and why), a plan or event with a date, the state of something they
are going through (started, finished, dropped, ordered, received), a goal and its progress, a measurement (weight,
hours, amount), a constraint (budget, schedule, place, language, health, a platform they use) and a document
they send. Write absolute dates: resolve "сегодня", "через две недели", "в следующем месяце" against the time of
the source message; when the date cannot be resolved, leave it out rather than guess.
```

### 6.2. Повторяющиеся просьбы — только личный и семейный контракт

```text
A topic the person keeps coming back to is a stable interest, not a one-off request. Before treating a request
as one-off, look at the visible conversation and the memory shown for earlier requests of the same kind; if
there are any, save the interest itself and keep it in a thread.
```

В общий фрагмент это правило не идёт, чтобы тихий обход групп не начал писать «X регулярно спрашивает…» про каждого
участника.

### 6.3. Ведение нитей: заменяет абзац о нитях в `MEMORY_WRITE_CONTRACT`

```text
## Threads
A thread is the timeline of one side of a person's or the family's life that will continue: a hobby, health or
weight, tastes in series or books, a trip, a repeated purchase, a goal, a work topic. Open one when a topic will
have more to come; a single episode, a general opinion or a one-off question stays a plain fact.
A thread lives in a memory area, not in a chat: a family thread is the same thread in the family group and in each
member's private chat. Put into a thread only records that everyone who sees the thread may see: a personal thread
takes personal and family records, a family thread takes only family records. When the person continues a family
matter in a private chat, save the record to the family memory, attach it to the family thread and tell them
"добавил в семейную нить «…»"; their personal opinions and feelings stay personal even on that topic. If it is
unclear whether a detail is shared or personal, ask. A record keeps its own subject, whoever it is about.
When something in a thread happens or changes, add an entry with the key of the thing that changed. The latest
entry for a key is its current state; earlier ones are its history. Take keys from the thread summary exactly;
make a new key only for a new thing. Fill only the fields you know:
- eventOn — the date it happens or happened, absolute;
- state — open, done or dropped, with a short label ("не решено", "досмотрела", "сдвинули");
- value and unit — a measurement;
- dueOn — a deadline;
- file — the workspace path of a document the person sent.
Save the fact and the entry in one `remember` call. For something that is not a fact about the person — your own
suggestion, a pause — use `manage_memory_thread` with `add_entry`. Never mark an entry done on your own guess:
only when someone said so, citing that message.
```

Примеры из разных областей:

```text
- "Опять заказал тот же кофе": entry key "кофе", eventOn today; no state.
- "Сегодня 83 кг": entry key "вес", value 83, unit "кг".
- "Досмотрела, концовка слабая": the series from the visible conversation, state done, label "досмотрела,
  концовка слабая"; if unclear which one, do not guess.
- "Сдать отчёт клиенту к 15-му": entry key "отчёт клиенту", state open, dueOn the 15th resolved to a date.
- "Решили всё-таки Postgres": entry key "БД проекта", label "Postgres"; the earlier decision becomes history.
- "Вот договор" with a file: read it, save a fact with its short summary and an entry with the file.
- "Спасибо, посмотрю" without naming an item: empty agreement, nothing to save.
```

### 6.4. Рекомендации — новый фрагмент для режимов с поиском

```text
## Recommendations
Before recommending something to watch, read, buy, visit or try, read the thread of that activity: tastes and
dislikes, the current state of each item and what you already suggested. Do not suggest an item that is done,
dropped or disliked, or one you already suggested that the person did not take up, unless they ask for it again;
if you mention such an item, say so ("вы уже смотрели", "я уже предлагал"). Say in a few words why each
suggestion fits this person. Then record what you suggested with `add_entry`.
```

### 6.5. Согласование с правилами групп

- В `GROUP_CONVERSATION_MEMORY_RULES` пункт «не стоит хранить: вопрос или просьбу к тебе» уточняется: «голый
  вопрос или просьбу без вкуса, плана, состояния, замера, ограничения или документа».
- Критерий нити из 6.3 («будет продолжение») заменяет «сильный сигнал» в `GROUP_MEMORY_DELTA_CONTRACT`.
- Тихий обход групп пока не получает `entry` и `add_entry`. Это доработка вместе с рабочими чатами (раздел 8).

## 7. Проактивность поверх нитей

### 7.1. Поводы — расчёт по ключам, без модели

Для каждого ключа активной нити код считает:
- последнюю дату;
- ритм — медиана промежутков, если событий ≥3 и промежутки регулярные (малый разброс), или если человек сам
  назвал период;
- динамику замеров;
- срок и состояние.

Отсюда поводы:

| Повод | Условие |
|---|---|
| «скоро пора снова» | ритм известен; ожидаемая дата − 7 дней (константа) наступила |
| «давно нет замера» | у ключа с замерами промежуток больше обычного в 1,5 раза |
| «срок близко» | `due_on` через ≤ 2 дня, состояние `open` |
| «срок прошёл» | `due_on` в прошлом, состояние `open`; в рабочем чате — вопросом |
| «скоро событие, а вопрос не решён» | в нити есть будущая `event_on` через 7 или 2 дня и открытые пункты |

**«Ещё есть» в момент `t`** — следующий повод по ключу не раньше `t + max(3 дня, M/4)`. В ритм `M` берётся не меньше
этого неполного промежутка. «Кончилось» — только со слов человека.

**Арифметика покрывается тестами** на граничные случаи и тестами свойств:
- «ещё есть» никогда не сдвигает повод раньше;
- прошедшее событие поводов не даёт;
- нерегулярные даты ритма не дают.

### 7.2. Проверки перед отправкой

Отказ, если:
- человек выключил инициативы;
- нить завершена, на паузе (последняя запись-пауза ещё действует) или заглушена;
- нить чувствительна;
- адресат не видит область нити (5.1);
- **этот же повод** уже отправлен. Повод = нить + ключ + своя дата. Это не лимит, а защита от того, что
  созревший повод уходил бы каждый день.

Тихие часы переносят отправку на их конец. **Лимитов на количество нет.** Внешние группы инициатив не получают до
режима рабочих чатов.

### 7.3. Подготовка содержания

Подготовка — внутренний ход ядра **по образцу тихого обхода групп** (`agent/lib/memory-review/`):
- ключ продолжения — `initiative:<id>`;
- авторизацию собирает backend из области нити;
- инструменты задаёт код: чтение памяти и нити, `web_search`, `web_fetch`, а также `submit_initiative` и
  `decline_initiative`.

Сценарии для этого не годятся: запуск сценария отправляет итоговый текст сразу, создаётся только из чата человека и
сохраняет инструменты записи.

**`submit_initiative`** принимает `summary` и 1–3 пункта (`title`, `why`, `url`). Код проверяет:
- адреса пунктов были открыты `web_fetch` в этом ходе;
- лимиты длины.

Не прошло проверку — молчание. Итоговый текст хода никуда не доставляется.

### 7.4. Сборка и отправка

Сообщение собирает backend из структуры:
- **строка «почему пишу»** — из данных нити («заказывали 3 раза, примерно раз в M дней»);
- **пункты**;
- **кнопки.** У «скоро пора снова» это «Помоги заказать» (обычный ход с подтверждениями), «Ещё есть» и «Не надо
  такого»; кнопки «Заказать» нет, потому что нет инструмента заказа.

**Одна инициатива — одно сообщение.** В наборе кнопок засчитывается одно нажатие, поэтому сводок нет.

**Первая инициатива каждому** одной строкой объясняет, что это и как выключить.

**Куда приходит инициатива по семейной нити** — туда, где нить вели последней:
- в личный чат члена семьи, который последним добавлял в неё записи;
- или в семейную группу, если нить вели там.

Так инициатива попадает тому, кто сейчас занимается делом, и не дублируется всей семье (вопрос 5 в разделе 14).
Инициатива по личной нити приходит в личный чат её хозяина.

Доставка — существующим путём Telegram. `proactive_deliveries` получает источник `initiative`.

### 7.5. Реакции

Нажатие записывается в нить при приёме вебхука (`source_kind = press`): это новая ветка в `reply-button-arrival.ts`.
Затем, как и сейчас, начинается обычный ход. Кнопки и их действие:
- «Ещё есть» → ритм сдвигается позже (7.1);
- «Не надо такого» → пауза нити на 30 дней; два раза подряд по одной нити → пауза до отмены;
- «Уже сделал» → `done` по ключу.

Текстовый ответ не считается откликом. К ходу, открытому нажатием, backend прикладывает содержание инициативы:
`<recent_proactive_deliveries>` показывает доставку только один раз.

### 7.6. Журнал и пробный режим

Таблица `initiative_decisions`:
- нить, ключ, повод;
- проверки и коды причин;
- вердикт;
- структура подготовки;
- режим `shadow` / `live`;
- ссылка на доставку.

**Пробный режим:** всё работает, но ничего не отправляется. Каждый по просьбе видит список «что бы я прислал и
почему» по тем нитям, которые ему видны (5.1), и отмечает полезное.

### 7.7. Наблюдаемость

- Коды логов `AGENT_INITIATIVE_*`:
  - повод;
  - вердикт с причиной;
  - подготовка (`submitted` / `declined` / `rejected`);
  - доставка;
  - реакция.
- **Метрики по человеку:**
  - поводы;
  - отправлено;
  - доля «полезно»;
  - доля «не надо».
- **Тревога владельцу** при всплеске числа инициатив одному человеку. Это только сигнал, он ловит ошибку кода (например,
  сломанную защиту от повторов), отправку не останавливает.
- **Пороги этапа 3 не держатся две недели** — тревога и разбор с владельцем. Автоматического выключения нет.

## 8. Рабочие чаты: что закладываем сейчас и что потом

**Сейчас, потому что иначе потом пришлось бы переделывать данные:**
- запись нити с ключом, состоянием, датой, сроком, замером, файлом, `note`;
- источник у каждой записи;
- нить принадлежит области, а «о ком» остаётся у факта;
- хронология по дате события;
- чтение с отбором и сводка по приоритету: сроки → открытое → текущее → события → документы;
- изменения нити проверяет backend по правилам области;
- закрыть пункт по своей догадке агент не может.

**Потом, вместе с режимом рабочих чатов** — всё это добавочные изменения без переделки данных:
- поле «ответственный» — проверенный участник чата;
- права участников: кто закрывает задачи, двигает сроки;
- инициативы в рабочий чат вопросами: «этап X должен был закрыться 15.11 — закрыт?». Источник — состояние нити, а не
  попытка понять из переписки, «что не обсуждали»;
- тихий обход групп получает `entry` и `add_entry`: отмечает сделанное, решения, сдвиги сроков;
- **открытый вопрос:** один проект в нескольких чатах. Сейчас нить принадлежит одной области, и для этого понадобится
  новый вид области. Устройство «нить принадлежит области» это не блокирует.

## 9. Данные и миграции

**`memory_thread_entries`** — новые необязательные поля:
- `source_kind`;
- источники `agent` / `press`;
- `key`, `key_normalized`;
- `state`, `label`;
- `event_on`;
- `value`, `unit`;
- `due_on`;
- `file_path`, `file_sha256`;
- `note`.

Ограничение «ровно один источник» заменяется проверкой по `source_kind`. Индексы — по нити и ключу, по сроку.

**Остальные изменения:**
- **`memory_threads`:** поля `subject_user_id`, `subject_participant_id`, `subject_conversation_id` остаются, но
  меняют смысл. Теперь это необязательное «чья линия» (5.1):
  - факты в нить они больше не ограничивают — меняется проверка в `memory-thread-write.ts`;
  - различение одноимённых нитей разных людей и защита от дублей работают по ним, как сейчас;
  - сохранённые данные не меняются.
- **«Проекты» убираются** (решение владельца 27.10). У проекта были две роли, обе переходят к нити:
  - «паспорт» нити-темы — теперь это сама нить, принадлежащая области (5.1);
  - разделение слотов свойств между темами — теперь по нити, к которой привязана запись.

  Миграция:
  - у 41 нити и 77 записей снимается ссылка на проект;
  - таблица `memory_projects` удаляется;
  - удаляется код вокруг неё: 11 файлов — создание нитей, поиск, слоты, тихий обход, защита от похожих записей;
  - из инструмента сохранения уходит вид нити `identity: "project"`.

  Проверено 27.10: у каждого проекта ровно одна нить, все 77 записей уже лежат в своих нитях, и ни одна не использует
  слот свойства. Поэтому поведение уже сохранённых данных не меняется.
- **Новые таблицы:** `initiative_decisions`; флаг «инициативы выключены» в настройках уведомлений (по умолчанию
  включены).
- **Существующие записи нитей и факты не переписываются.** Старые записи остаются без новых полей.
- **Миграции** — `npm run migrate` в контейнере. Проверка — интеграционными тестами Docker: нити в личке, семье и
  группе, изоляция областей, тихий обход групп без изменений.

## 10. Этапы и проверки готовности

**Этап 1. Нити.**
- Что делаем:
  - устройство записи (5.3–5.4), принадлежность области (5.1), ключи (5.5), документы (5.6);
  - `entry` в `remember`, `add_entry` и `merge`;
  - сводка (5.8) и чтение с отбором (5.9);
  - промпты (раздел 6);
  - убрать «проекты» (раздел 9).
- Проверка: прогон ~50 реальных сообщений на боевой модели, с нынешними и новыми промптами. Набор вне git, личные
  сообщения — с согласия авторов. В наборе:
  - личные ходы со вкусами, покупками, планами, замерами, документами;
  - групповые хвосты;
  - шумовые сообщения;
  - диалоги на повтор рекомендаций.
- Меряем:
  - заводятся ли нити, где у темы есть продолжение;
  - верны ли ключи и не разъезжаются ли;
  - верны ли состояния и даты;
  - прикрепляются ли документы;
  - нет ли повторов в советах;
  - сколько лишних записей в группах.
- Порог:
  - нужное сохраняется не меньше чем в 70% случаев;
  - лишнего не больше 10%;
  - ноль повторов отвергнутого.
- Затем живой чат.
- **Контрольная точка:** если наполнение ниже 50%, до этапа 2 — разговор с владельцем.

**Этап 2. Поводы и пробный режим.**
- Что делаем: расчёт (7.1), проверки (7.2), подготовка (7.3), журнал и пробный режим (7.6), показ «за чем я
  слежу».
- Готовность: две недели пробного режима; не меньше половины «прислал бы» — полезно; не больше одной неуместной
  инициативы за две недели; ноль утечек между областями.

**Этап 3. Отправка.**
- Что делаем: по умолчанию у всех, без лимитов; сборка (7.4); реакции (7.5).
- Готовность через 4 недели: полезных не меньше 40%, «не надо» не больше 30%.

**Этап 4. Интересы, каталоги, почта.**
- «Новинки X» — еженедельный сценарий, который человек заводит согласием из своего чата. Монитор не подходит: он
  живёт не дольше 14 дней.
- Вкус + новинка в каталоге — когда выбран источник.
- Почта как источник событий — если Google подключён и человек согласен, только чтение.

**Этап 5. Рабочие чаты** — отдельной спецификацией, на устройстве из раздела 8.

## 11. Безопасность и приватность

- **Подготовка инициатив** — только чтение и узкий набор инструментов. Страницы и файлы — недоверенные данные.
- **Чувствительные факты и документы** не дают поводов, реквизиты не попадают в краткое содержание.
- **Секреты не должны жить в памяти:** подготовка читает память. Если секрет уже лежит в записи, сначала убрать его.
- **Видимость по областям (5.1)** — для нитей, пробного списка и инициатив:
  - личное — только хозяину;
  - семейное — всем членам семьи;
  - групповое — этой группе.
- **Запись в семейную нить из лички** раскрывает её семье. Поэтому агент сообщает «добавил в семейную нить», запись
  можно отменить, а личное в семейную нить не кладётся.

## 12. Будет ли это работать

### 12.1. Что подтверждают исследования

- **Решать «вмешаться ли» лучше не моделью.** Отдельный контроллер выбирал момент лучше модели (AUC 0,738 против
  0,668). Самопроверка моделью в промпте вместо контроллера стоила 12,7 пункта F1. Наш контроллер — правила, данных для
  обучения нет, но разделение то же: поводы считает код, модель готовит содержание.
- **Модели встревают без нужды.** В ProEvent Qwen-3 32B ложно срабатывал в 96,6% моментов, где делать ничего не нужно.
  Шаг «нужно ли действовать» снизил ложные срабатывания DeepSeek-V3.2 с 96,9% до 26,5%. Поэтому повод даёт код, а
  модель может только отказаться.
- **Момент важен.** В лаборатории помощь в подходящий момент принимали в 68% случаев, в случайный — в 44%.
- **Пачка лучше потока.** Пачка три раза в день улучшила внимание и снизила стресс, пачка каждый час почти ничего не
  дала. Владелец решил число инициатив не ограничивать. Вместо лимита работают: одна инициатива на повод, защита
  от повторов, «Не надо такого» и метрики.
- **Предпочтения модель сама не удерживает.** У большинства моделей точность следования высказанным предпочтениям
  падает ниже 10% к 10-му ходу (PrefEval). Отсюда явное состояние пунктов в нити и чтение нити перед советом.
- **Числам от модели не доверять** — самооценки уверенности плохо откалиброваны. Отсюда: модель пишет ключи и
  состояния, числа считает код.
- **Повторные покупки на скудных данных** лучше предсказываются с исходной оценкой. Отсюда «регулярность или
  названный период» и «ещё есть» как нижняя граница.
- **Hark, Gemini Spark, OpenAI dots, Meta Muse** опираются на события с датами и спрашивают перед действием.
- **Объяснение причины и управление со стороны человека** снижают ощущение слежки.
- **Структурированная, привязанная ко времени память** (Zep: факты со сроком действия; ChronoProfiler: устойчивость
  свойств во времени; QUMem: типизированные записи с датами) работает лучше плоской. Запись нити с ключом и датой —
  тот же принцип.

### 12.2. Где будет «рандом» и что с этим делаем

1. **Агент не заводит и не ведёт нити** — главный риск. Сейчас в личке их 3. Если правки промптов не помогут, данных не
   будет и система будет молчать. Безопасно, но бесполезно. Контрольная точка — этап 1.
2. **Разъехавшиеся ключи.** Защита из 5.5 и замер на этапе 1.
3. **Даты словами** («примерно через две недели») поводов не дают. Это честное ограничение, а не ошибка.
4. **Ритм там, где его нет.** Только регулярные промежутки или названный человеком период; пробный режим.
5. **Подготовка, которая всегда что-то находит.** Проверка структуры кодом, право отказаться, пробный режим.
6. **Устаревшие внешние данные.** В сообщении — дата данных и пометка «не проверено».

### 12.3. Где будет неуместно

- **Чувствительные темы** исключены.
- **Границы семьи.** Семейная нить видна всей семье, поэтому:
  - личное в неё не кладётся;
  - запись из лички в семейную нить агент объявляет, и её можно отменить;
  - инициатива по семейной нити приходит тому, кто её вёл последним, а не всем.
- **Инициативы включены, а человек об этом не просил:** объяснение в первой инициативе, «почему пишу» в каждой,
  кнопка «Не надо такого».
- **Нет лимита:** если поводов созреет много сразу, уйдёт несколько сообщений подряд. Это решение владельца;
  следим по метрикам.
- **Выводы о «пробелах» и чувствах** агент не делает. Желания — только со слов человека, как цель в нити.

### 12.4. Вердикт

Подход рабочий, если нити наполняются. Тогда агент ведёт линии жизни в разговоре: этапы, сроки, решения,
документы, советы без повторов. Это польза уже на этапе 1, даже без единой инициативы. А инициативы, привязанные
ко времени и явным данным, считает код. «Догадок о скрытых нуждах» не будет.

Слабое звено одно — будет ли агент заводить и вести нити. Этап 1 это измеряет до того, как строить проактивность.

## 13. Что не меняется

- Изоляция областей памяти и то, какой чат какую память видит: личка — личную и семейную, семейная группа —
  семейную, внешняя группа — свою.
- Факты памяти и `remember` как единственный способ их сохранить.
- Защита от дублей нитей по похожести названия.
- Завершение нити по словам человека или подтверждённому итогу.
- Не больше 2 нитей в разговоре автоматически.
- Тихий обход групп, кроме уточнения критерия нити.
- Слоты свойств для свойств человека.
- Восемь ролей записей.

## 14. Открытые вопросы владельцу

1. **Документы** — факт с кратким содержанием плюс запись нити с файлом, без индекса содержимого (5.6). Это уточняет
   решение 21.09. Так?
2. **Подготовка содержания** — фоновый ход модели по уже созревшему поводу (7.3). Это не разбор памяти, но
   отдельный проход. Допустим?
3. **Источник каталога** фильмов и сериалов для этапа 4: ключ неофициального API Кинопоиска или пока только сайт
   площадки?
4. **Запись в семейную нить из лички.**
   - Вариант А: автоматически, когда человек продолжает общую линию, с сообщением «добавил в семейную нить» и отменой
     (5.1).
   - Вариант Б: как сейчас, только по прямой просьбе сделать общим.
   - Рекомендация — А: при Б вести семейные нити из лички не получится.
5. **Куда приходит инициатива по семейной нити.**
   - Вариант А: туда, где нить вели последней (7.4).
   - Вариант Б: всегда в семейную группу.
   - Вариант В: всем членам семьи в личку.
   - Рекомендация — А.

## 15. Чем редакция 4 отличается от 3

**Правка 4.3:** поле нити «о ком» становится необязательным «чья линия» (5.1, раздел 9):
- оно не ограничивает, какие факты кладутся в нить;
- оно различает людей по проверенному участнику — например, двух Алексеев в одном чате;
- у фактов «о ком» своё, как и было.

В первой версии правки поле убиралось совсем, а людей предлагалось различать названием нити. Это ломалось на
тёзках: защита от дублей сочла бы «Учёба Алексея» второго Алексея дублем первой.

**Правка 4.2:** «проекты» убираются по решению владельца, их роль берёт нить (раздел 9). Вопрос о них снят, остальные
вопросы перенумерованы.

**Правка 4.1:**
- семейные нити видны и ведутся из личных чатов (5.1);
- правило «в нить кладутся только записи, которые видят все, кто видит нить»;
- запись в семейную нить из лички с сообщением и отменой;
- доставка инициатив по семейным нитям (7.4);
- вопросы о записи в семейную нить из лички и о доставке (сейчас 4 и 5).

Убрано вместе с отдельной матрицей:
- тип нити `kind` (habit / plan / goal / collection / interest) — расчёты теперь идут по содержимому;
- поля `startsOn` / `endsOn` в `remember` — даты стали полями записи нити;
- статусы через слоты свойств — их заменили ключи записей;
- исключение «можно сохранять свои слова» («Предложено…») — заменено записью нити `agent`, это не факт памяти;
- набор кнопок и бюджеты из редакции 2 — заменены решениями владельца (раздел 2).

Добавлено:
- принадлежность нити области вместо «о ком»;
- одна запись с необязательными полями: ключ, состояние, дата, замер, срок, файл, `note`;
- источники `agent` / `press`;
- документы;
- слияние нитей;
- чтение с отбором;
- сводка по приоритету;
- критерий «будет продолжение»;
- раздел о рабочих чатах;
- вопрос о «проектах».

Сохранено из редакций 2–3 — то, что подтвердила проверка по коду:
- подготовка как внутренний ход по образцу тихого обхода, а не сценарий;
- проверка подготовки кодом;
- одна инициатива — одно сообщение;
- нажатие записывается при приёме;
- пробный режим у каждого свой;
- монитор не годится для «новинок».
