# Быстрый выпуск и выкатка

Статус: в работе, #577.

## Зачем

От слияния в `main` до новой версии на проде уходит ~38 минут: 15 минут сборки на GitHub до кнопки и
~23 минуты выкатки после неё. Замер выкатки v0.81.1 (25.11.2026, журнал `osinara-deploy.service`):

| Шаг | Время | Бот отвечает |
|---|---|---|
| Ожидание таймера и подготовка | 0:51 | да |
| Скачивание пяти образов | 4:13 | да |
| Копия папок песочниц (`tool-environments`, `workspace-data`) | 14:24 | да |
| Остановка, копия базы и ключей Google, контрольные суммы | 2:41 | нет |
| Запуск новой версии | 0:48 | нет |

Последние 12 выкаток — 17–22 минуты каждая. Сборка на GitHub: тесты 9,5 мин (повторный прогон того же
кода, что уже прошёл в PR), сборка образов 5,3 мин.

Причины:

1. Метки версии (`LABEL org.opencontainers.image.*`) стоят в общей базе `first-party-node` `Dockerfile`.
   С ними каждый релиз сбрасывает кэш сборки всех образов поверх неё: `npm ci` при неизменном списке
   пакетов, установка ~124 пакетов в песочницу. Образы получают новые слои, сервер скачивает 12 слоёв.
   Блоки на чистой `node-base` (FFmpeg, проверка виджетов) берутся из кэша — проверено по логу CI v0.81.1.
2. Папки песочниц (6,5 ГБ на 25.11, 3,2 ГБ на 20.11) сжимаются целиком в `tar.gz` на одном ядре, на самом
   низком приоритете диска (#558), затем архив перечитывается для проверки. Из 6,5 ГБ: 1,4 ГБ — файлы чатов,
   5,1 ГБ — окружения инструментов, из них кэши: `<чат>/cache/` (pip, Playwright, `XDG_CACHE_HOME`) и
   `<чат>/home/.cache/` (Chrome для puppeteer). 112 тыс. файлов, обход без чтения — секунды.
3. Пока бот остановлен, `SHA256SUMS` считается по всем архивам, включая многогигабайтные копии песочниц,
   и сверяется дважды.

## Решения владельца (25.11.2026)

- Шаг 1 согласован: метки версии не ломают кэш сборки; большие копии не проверяются во время простоя.
- Шаг 2, вариант А: копия папок песочниц переносит только изменившиеся файлы; неизменённые — ссылки на
  прошлую копию; кэши (pip, Chrome и прочее в `cache/` и `home/.cache/`) не копируются. Три копии остаются.
- Шаг 3 согласован: на `main` не гонять тесты повторно, если ровно то же содержимое кода уже прошло оба
  набора проверок.
- Инструкцию деплоя поправить под все изменения.

Не входит: скачивание образов и копия до нажатия кнопки (обсуждалось как следующий шаг к 2–3 минутам).

## Что меняется

1. **Сборка образов.** Метки ставит CI (`labels:` у `docker/build-push-action`) на готовый образ; из
   `Dockerfile` уходят `ARG OCI_*` и `LABEL`, стадия `first-party-node` заменяется на `node-base`. Найдено на
   ревью: `version` в `package.json`/`package-lock.json` меняется каждым релизом и так же сбрасывал бы кэш
   `npm ci` — `npm ci` ставит пакеты из копий с обнулённым `version` (стадия `package-manifests`).
2. **Копия песочниц** (новый модуль `scripts/production-deploy/live-copy.sh`: `backup.sh` упёрся бы в предел
   500 строк для модулей контроллера). Вместо `tar.gz` — папка `<том>/` в комплекте
   копии, `rsync` в контейнере образа приложения (в `runtime` добавляется пакет `rsync`), `nice`/`ionice -c 3`
   как раньше. `--link-dest` на ту же папку в последней готовой копии: неизменённые файлы — жёсткие ссылки
   (одни и те же байты на диске для всех копий). Исключения только для `tool-environments`: `/*/cache/`,
   `/*/home/.cache/`. Сокеты и устройства не копируются (как раньше у `tar`). Код выхода 24 (файл исчез во
   время копии) — событие и продолжение, как код 1 у `tar`; код 23 — так же, но только если все сообщения
   `rsync` о файлах, изменённых во время чтения (`read errors mapping`, найдено на ревью); остальные
   ненулевые — отказ до остановки бота. Старый комплект во время простоя только переименовывается в
   `.retired.<имя>`, а удаляется после запуска новой версии: комплект из ~112 тыс. файлов удалялся бы на
   медленном диске прямо в простое (найдено на ревью).
3. **Контрольные суммы.** `SHA256SUMS` — только по файлам, сделанным при остановленном боте
   (`postgres.dump`, архив ключей Google). Файлы папок проверяет `rsync` при переносе.
4. **CI.** Новая задача перед тестами на push в `main`: если дерево коммита совпадает с деревом родителя, у
   которого есть успешный push-прогон этого же workflow с успешными «Docker Compose test suite» и «Memory
   retrieval evals», тесты пропускаются, выпуск идёт сразу; иначе — полный прогон. Ручной запуск
   (`workflow_dispatch`) всегда гоняет тесты. Логика — в `scripts/ci/tested-tree-reuse.sh` с тестами.
5. **Инструкция деплоя**: устройство CI, комплект копии, восстановление папок песочниц, общие байты копий.
6. **После выпуска**: промпт дежурного — новый комплект копии (папки вместо двух архивов).

## Когда готово

- Тесты на новую копию, контрольные суммы, метки и переиспользование проверок проходят в CI.
- Первая выкатка с новым кодом прошла `succeeded`; комплект копии — `postgres.dump`, архив ключей Google,
  `SHA256SUMS`, две папки.
- Вторая выкатка: копия песочниц — минуты, а не 14; сервер скачивает только изменившиеся слои.
- Push в `main` после релизного PR выпускает релиз без повторных тестов.

## Шаги

1. Тесты: копия песочниц (команда, исключения, `--link-dest`, коды выхода), состав комплекта и суммы,
   метки в CI, переиспользование проверок (скрипт с поддельными `gh` и `git`).
2. Реализация: `backup.sh`, `main.sh`, `Dockerfile`, `ci-release.yaml`, `scripts/ci/tested-tree-reuse.sh`.
3. Проверка поведения `rsync` на настоящих файлах (ссылки, исключения, сокеты, код 24).
4. Инструкция деплоя, описание выпуска.
5. Выпуск, выкатка, проверка комплекта копии на сервере, правка промпта дежурного.
