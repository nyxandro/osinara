# План улучшения памяти и поиска: порядок работ и контекст

Документ — рабочее задание для новой сессии агента. Он самодостаточен: в нём есть
состояние проекта, замеры боевого окружения, порядок задач, способ проверки каждой и
правила, которые нельзя нарушать. Записи (issues) в GitHub содержат разбор каждой
проблемы; этот документ задаёт последовательность и связывает их между собой.

Дата составления: 2026-09-19. Состояние репозитория на момент составления: `develop` = `fe56336`.

## 0. Как начать работу

1. Прочитать этот документ целиком, до конца, включая раздел «Чего делать нельзя».
2. Выполнить «Задачу 0» ниже — без неё разъедутся номера миграций.
3. Дальше идти по списку задач строго по порядку, сверху вниз. **Одна волна — одна
   ветка — один PR**, внутри волны каждая задача — отдельный коммит. Не брать следующую
   задачу, пока предыдущая не проверена.
4. Перед каждой задачей открыть её запись в GitHub **вместе с комментариями**: у
   половины записей в комментариях есть поправки, меняющие вывод исходного текста.

Владелец дал полное добро и вопросов принять не может. **Все решения принимать
самостоятельно**, ничего не откладывать до его ответа и не останавливаться в ожидании.
Принятое решение записывать в описание PR — утром он читает результат, а не согласует ход.

### Ловушка тестового прогона, на которую уже напоролись

Файлы интеграционных тестов делят одну базу и идут последовательно. Некоторые тесты
считают строки в общих таблицах **без фильтра**, а некоторые оставляют строки после себя.
Добавление нового файла теста меняет порядок и может уронить совершенно посторонний тест.
Один такой случай уже починен (`runtime-admission-reconciliation.integration.test.ts` теперь
убирает за собой). Если после добавления теста падает что-то, не связанное с задачей —
искать не в своей правке, а в общем состоянии базы между файлами.

## 4. Правила выполнения каждой задачи

Порядок действий, одинаковый для всех задач:

1. **Изучить.** Прочитать запись и комментарии к ней. Найти существующий путь исполнения в
   коде: модуль, его тесты, соседние механизмы. Проверить, нет ли уже частичной
   реализации — несколько записей описывают механизмы, которые частично существуют
   (подкрепление, конфликты, квоты). Новый код поверх старого писать нельзя: сначала
   понять, что есть, потом решить, дополнять или заменять.
2. **Проверить версии.** Для любой библиотеки, SDK или расширения БД — определить
   установленную версию и свериться с её документацией, а не с памятью. Eve `0.40.0`
   закреплена, документация в `node_modules/eve/docs/`, публичные типы в
   `node_modules/eve/dist/src/public/`.
3. **Снять замер «до».** Для задач, которые меняют качество выдачи или состав памяти —
   зафиксировать числа на боевой базе или на выборке до правки. Без этого «стало лучше»
   недоказуемо.
4. **Написать падающий тест.** Сначала тест, определяющий ожидаемое поведение; убедиться,
   что он падает по нужной причине; потом реализация.
5. **Реализовать** — наименьшее полное production-решение. Без заглушек, без придуманных
   значений по умолчанию для обязательных данных, без скрытых повторов. Ошибки,
   доходящие до пользователя, — на русском, с кодом вида `AGENT_...`.
6. **Проверить.** Объём проверок по риску: точечная правка не требует полного прогона,
   изменение общих контрактов и схемы — требует, включая docker-прогон с миграциями.
7. **Снять замер «после»** и сравнить с «до».
8. **Самопроверка.** Перечитать собственный диff: не осталось ли мёртвого кода, неиспользуемых
   импортов, отладочных логов, временных файлов. Затем — отдельным субагентом независимое
   ревью нетривиальных изменений: дать ему согласованные требования, точный список файлов и
   фокус проверки; субагент только читает и не правит.
9. **Оформить.** Отдельный коммит на задачу внутри ветки волны. Сообщение на русском по
   образцу истории репозитория, в теле — `Закрывает #N.` и объяснение, что было не так и
   почему сделано именно так.

### Ветки, слияние и порядок

Работает один автор, задачи идут по очереди, параллельных правок нет — поэтому конфликтов
при слиянии взяться неоткуда, если держаться этого порядка:

1. Ветка на **волну**, а не на задачу: `feat/memory-wave-1-instruments` и так далее.
   Ответвлять от свежего `develop`.
2. Внутри волны — отдельный коммит на каждую задачу, с `Закрывает #N.` в теле.
3. Закончив волну: полный прогон в Docker. **Зелёный — открыть PR, описать волну целиком и
   слить самостоятельно.** Красный — чинить, не сливая.
4. Следующую волну ответвлять от `develop`, уже содержащего предыдущую. Тогда каждая волна
   видит результаты прошлой, зависимости между задачами разрешаются сами, а номера миграций
   идут подряд без столкновений.

Почему не ветка на задачу: задачи внутри волны связаны (например, кривая забывания считает по
счётчику использования из соседней задачи), и в отдельных ветках их пришлось бы выстраивать
цепочкой — вот там конфликты и появляются. Плюс полный прогон занимает около восьми минут, и
гонять его двадцать раз вместо шести — это лишние часы ночью.

Почему не коммиты прямо в `develop`: если волна окажется неудачной, откатить одну ветку
одним движением проще, чем выковыривать перемешанные коммиты. И PR даёт владельцу страницу,
где утром видно, что сделано и почему.

Точечные тесты гонять на каждую задачу, полный прогон — на волну.

### Нумерация миграций

Следующий свободный номер — **105** (после слияния ветки с `104`). Номер занимать в момент
написания миграции, а не заранее. Если между задачами появилась чужая миграция — перенумеровать
свою, а не занимать номер повторно.

### Формат записей в GitHub

Если по ходу работы обнаружится новая проблема — завести запись в том же стиле, что
существующие: «Что видит пользователь», «Как это устроено сейчас», «Доказательства»,
«Что предлагается», «Цена и риски», «Что осталось непроверенным». Доказательства — замеры и
ссылки `файл:строка`, а не рассуждения.

### Волна 1. Приборы. Ничего не ломает, всё остальное на них опирается

#### Задача 1 — запись #197: числа о работе поиска в логах

**Почему первой из содержательных.** Пять других записей упираются в то, что эффект правки
нечем измерить. Поведение поиска не меняется, риск нулевой, а после выкладки данные копятся
сами, пока идут следующие задачи.

**Что сделать.** Дополнить существующую строку `AGENT_MEMORY_RETRIEVAL_METRICS`
(`agent/lib/prompt/turn-blocks.ts:320`) числами: длина запроса в символах, число кусков
запроса, сколько кандидатов дала каждая из трёх веток, лучший счёт каждой ветки **до
применения порога**, упёрлись ли в `MEMORY_RETRIEVAL_CANDIDATE_LIMIT`.

Счёт до порога — ключевое. Иначе не видно, что именно отсекается, а ради этого всё и делается.

Значения придётся пробросить из `memory-retrieval-repository.ts` наверх. Запрет на пересечение
границы модели остаётся: числа идут в лог, не в подсказку. Этот запрет закреплён тестом
`agent/lib/memory-retrieval-diagnostics.test.ts` — не ломать его.

**Приватность — конструктивное требование, а не пожелание.** В лог не попадает ни слова из
запроса и ни слова из записей. Только числа. Модуль наблюдаемости построен по этому принципу,
держаться его.

**Дополнительно:** правило тревоги в `infra/monitoring/` на долю запросов с пустой выдачей.
Сейчас пустых выдач не бывает вовсе — значит правило поймает и поломку эмбеддера, и
деградацию после правок поиска.

**Готово, когда:** в боевых логах видно распределение счетов по веткам; по логам можно
ответить, в какой доле ходов словесные ветки дали хоть одного кандидата.

#### Задача 2 — запись #210: видимость непроиндексированных записей

Маленькая задача, делается заодно с предыдущей: счётчик записей в состоянии

Повторную попытку индексации (пункт Б записи) делать только если она укладывается в правило
о повторах: ограниченная, по признаку временного сбоя, а не по таймеру.

#### Задача 3 — запись #198: выборка для замеров качества

**Зачем.** Нынешняя приёмка — 25 искусственных записей и короткие чистые запросы. На такой
выборке калибровать пороги бессмысленно, а следующая волна именно этим и займётся.

**Что сделать.** Выборка v3 в том же стиле, что v1 и v2 (версионированная, с зафиксированными
базовыми числами): 200–300 записей, разные области памяти, пересекающиеся темы, близкие по
смыслу но разные по сути записи. Запросы — живые: длинные, многотемные, с обращением к боту,
с эмодзи, с опечатками, из голосовой расшифровки без знаков препинания, с «ё» против «е».
Отдельные категории под то, что сейчас не покрыто.

**Сохранить нынешнее свойство:** провалы записываются как признанный долг, а не замазываются.
Именно так сделано в v2 — это хорошая практика.

**Не копировать** подход соседнего проекта: их `rag-eval` проверяет контракт на захардкоженных
ответах, реального прогона по корпусу там нет. Наша конструкция сильнее.

**Готово, когда:** прогон v3 даёт воспроизводимые числа, и они зафиксированы в коде как базовые.

### Волна 2. Отбор кандидатов. Самый заметный эффект для пользователя

#### Задача 4 — записи #192 + #195 + #196 одной работой

**Почему вместе.** «ИЛИ» без пересмотра порогов упрётся в то, что слабые совпадения всё равно
отсекаются. Пересмотр порогов без «ИЛИ» нечего отсекать. «ё» правится в том же модуле
подготовки запроса. Порознь каждая даст половину эффекта.

**Что сделать.**

1. Новый модуль подготовки поискового запроса: снять обращение к боту в начале, эмодзи,
   разметку Markdown, свести «ё» к «е». Очищенный текст идёт и в словесные ветки, и в
   эмбеддинг — снятие обращения улучшает и смысловую ветку.
2. Собирать условие словесных веток через «ИЛИ» вместо «И». Сейчас `websearch_to_tsquery`
   требует одновременно все слова вопроса, включая предлоги и местоимения в ветке `simple`.
3. Миграция: вычисляемая колонка `search_vector` со сведением «ё» к «е». Колонка вычисляемая,
   PostgreSQL пересчитает сам; переиндексация векторов не нужна. **Морфологическую ветку не
   трогать** — там стеммер уже сводит «ё» к «е» сам.
4. Пересмотреть отсечение. Пороги `0.05 / 0.05 / 0.78` после перехода на «ИЛИ» теряют смысл.
   Проверить на выборке v3 два варианта: плавающее отсечение от лучшего результата плюс
   абсолютный нижний предел — и полный отказ от отсечения с переходом на взвешенное
   объединение. Второй вариант работает в соседнем проекте: там словесная ветка сломана так же,
   но не мешает, потому что просто добавляет ноль, а кандидат остаётся.

**Риск:** «ИЛИ» тянет в кандидаты слабые совпадения по одному частому слову. Сдерживается
отсечением и лимитом кандидатов, но величину подбирать замером на v3, а не на глаз.

**Готово, когда:** на выборке v3 доля запросов, где сработала хотя бы одна словесная ветка,
выросла; полнота не упала; числа зафиксированы.

#### Задача 5 — запись #194: лучший кусок запроса вместо среднего

Длинный многотемный запрос сейчас усредняется в один размытый вектор, и не находится ни одна
из тем. Считать близость с каждым куском запроса отдельно и брать максимум.

Вызовов к эмбеддеру не прибавляется — они уже делаются, сейчас результат просто схлопывается.

### Волна 3. Индекс и куски. Один реиндекс на всё

#### Задача 7 — запись #201: довести векторный индекс до рабочего состояния

**Решение владельца:** индекс не сносить, а заставить работать.

**Чего нельзя нарушить:** правила доступа вшиты в предикат до ранжирования

`hnsw.iterative_scan` и `hnsw.ef_search`, выбрать режим порядка.

индекс.

**Честная оговорка:** на нынешних 1712 векторах перебор занимает миллисекунды. Это работа
на вырост и ради задачи 5, а не по сегодняшней боли.

#### Задача 8 — записи #193 + #202 одним реиндексом

**#193 — шапка с сущностью.** В вектор сейчас идёт голый текст записи, без указания, о ком

Класть в вектор текст с шапкой: субъект и вид записи. **Инвариант «кусок — точный срез
оригинала» ломать нельзя** (`memory-index-repository.ts:149-157`, он защищает от рассинхрона

**#202 — размер куска.** Сначала прогнать токенизатор модели на реальных записях и получить

### Волна 4. Состав выдачи: какие двенадцать из сорока

#### Задача 9 — запись #203: журнал показов

**Измеренный симптом:** половина показов — повтор того, что модель уже видела; одна запись
занимала слот в 14 ходах из 29.

Таблица показов: какие записи и чья карточка профиля уже показывались в этой прикладной
сессии, с номером хода. Запись, показанная в последние N ходов, в автоподборку не включается.

**Окно считать в ходах, а не во времени** — тогда тихий чат ведёт себя как активный.

**Ограничение только для автоподборки.** Явный поиск `search_memories` должен видеть всё:
если модель целенаправленно ищет факт, скрывать его нельзя.

Карточку профиля текущего автора вернуть через более длинное окно или когда человек стал
предметом обсуждения.

**Замер «после» обязателен:** доля повторных показов должна упасть, а число уникальных
записей на ход — вырасти.

#### Задача 10 — запись #206: модель отмечает, чем воспользовалась

**Измеренный симптом:** подкрепление стоит у 9 записей из 1465, максимум счётчика — 1.
Полезная и ни разу не пригодившаяся записи для ранжирования неразличимы.

Директива в конце ответа со ссылками на использованные записи; транспорт вырезает её до
отправки человеку. Подкрепляются **только записи, показанные в этом же ходу** — ссылка на
непоказанную отклоняется и пишется в лог.

**Счётчик использования держать отдельно от счётчика подтверждений.** «Факт наблюдали
заново» и «запись пригодилась в ответе» — разные вещи; смешав их, потеряем оба смысла.

**Критично — место инструкции.** Замер соседнего проекта вслепую на 18 реальных ходах, по два
сэмпла: правило в блоке режима дало 1 ответ с директивой из 36, условное напоминание — 2 из 36,
обязательное напоминание сразу после блока записей памяти — 34 из 36. Разница не в
формулировке, а в месте. У нас другая модель, поэтому **свой замер обязателен**, но начинать
стоит с обязательного напоминания сразу после записей.

**Обязательный лог** того, как часто правило соблюдается: иначе неизвестно, работает ли
механизм вообще.

**Тест на то, что остаётся от ответа после вырезания директивы** — если разбор не сработает,
служебный тег уйдёт человеку.

#### Задача 11 — запись #207: кривая забывания вместо бонуса свежести

**Зависимость: делать после задачи 10.** Стойкость записи растёт от подкреплений, а сейчас
подкреплений практически нет — считать будет не от чего.

Доступность записи `R = exp(-возраст / S)`, где `S = S0 × (1 + ln(1 + n))`, `n` — число
подкреплений. Базовая стойкость зависит от вида записи. Порядок величин из соседнего
проекта: эпизод 30 дней, итог обсуждения 60, смысловые виды 180 — **проверить на своей
выборке, не принимать на веру**.

Применять **множителем** на итоговый ранг, а не слагаемым, с нижней границей — чтобы старая
запись уступала место, а не исчезала. Порог доступности — только для автоподборки; явный
поиск видит всё. Старение — это про приоритет в двенадцати слотах, а не про удаление.

Формулу придётся продублировать в SQL, потому что ранг считается в запросе. **Расхождение
двух копий — тихая ошибка**, закрыть тестом.

#### Задача 12 — запись #200: замер после волны

К этому моменту околодубли должны были уменьшиться за счёт задач 9 и 14. Снять замер: сколько
слотов из двенадцати реально уходит на записи, говорящие одно и то же.

**Важная поправка, уже внесённая в запись:** отсев по порогу близости применять нельзя.
Настоящие дубли дают ≈ 0.934, разные факты об одном человеке 0.916–0.924, диапазоны
перекрываются. Порог, который поймает дубли, молча выбросит независимые сведения. Если после
замера проблема осталась — искать признак, отличающий пересказ от отдельного факта, а не
крутить коэффициент.

### Волна 5. Что попадает в память

Эта волна меняет схему и контракт записи. Она тяжелее предыдущих и делается последней из
содержательных.

#### Задача 13 — запись #205: слот свойства

«Кофе с сахаром» и «кофе без сахара» живут рядом как равные записи. Поля, обозначающего, о
каком свойстве субъекта идёт речь, нет.

Поле слота у видов profile / preference / fact / family_shared. Новая запись того же субъекта
с тем же слотом переводит прежнюю в неактивное состояние. **Прежняя версия не удаляется**, а
помечается замещённой: история остаётся в экспорте и в списке памяти.

**Механизм конфликтов не трогать** — он решает другую задачу: показать обе стороны
неразрешённого противоречия источников. Смена предпочтения во времени — не противоречие.

**Главный риск — слишком общий слот.** Модель назовёт слот «еда» и затрёт независимые факты,
причём молча. Это опаснее, чем не сработавшее замещение. Нужны ограничение на длину и показ
модели уже существующих слотов субъекта.

#### Задача 14 — запись #208: проверка соседей при записи

Перед сохранением смыслового сведения посчитать вектор содержимого и найти активные записи
того же субъекта с близостью выше порога. Есть такие — вернуть модели отказ со списком
кандидатов и тремя выходами: подкрепить существующую, назвать слот, признать отдельным.

**Код сам ничего не склеивает.** Порог служит только для показа кандидатов; решает модель,
которая видит и текст, и контекст разговора. Это прямое следствие того, что по близости
пересказ от разного факта не отличить.

**Без сервиса эмбеддингов гейт пропускает запись** — недоступность вспомогательной проверки
не должна ронять сохранение памяти.

#### Задача 15 — запись #204: разбор видит, что уже записано

Тихая проверка памяти получает только сообщения пакета и не знает, что уже сохранено. Поэтому
записывает то же другими словами.

Подавать в подсказку разбора активные записи этой беседы и хвост уже проверенных сообщений.
Оба блока — недоверенные данные, экранировать тем же способом, что и текст пакета. Объём
ограничить релевантной выборкой, иначе на долгоживущем чате подсказка разрастётся.

**Посчитать удорожание разбора** до внедрения: это прямой расход на модель на каждом пакете.

**Инструкция должна явно разрешать и уточнение, и отдельную запись** — иначе модель перестанет
записывать новые подробности, увидев похожее.

#### Задача 16 — запись #213: даты событий

Необязательная дата события у записей о произошедшем плюс окно «с — по» в поиске.

**Дата события не должна влиять на старение:** событие десятилетней давности, о котором
рассказали сегодня, — свежее знание. Смешать эти оси значит спрятать только что рассказанное.

**Придумывать даты нельзя.** Не известно из разговора — поле пустое. У существующих 194
эпизодов даты не будет никогда, и это надо принять, а не заполнять задним числом.

**Спрос неизвестен.** В логах текста запросов нет; после задачи 1 можно будет оценить, часто ли
спрашивают с привязкой ко времени. Если редко — задача уходит вниз.

### Волна 6. Эксплуатация

#### Задача 17 — запись #209: поиск без сервиса эмбеддингов

Сейчас вектор запроса берётся до поиска и безусловно (`memory-retrieval.ts:115`). Эмбеддер
недоступен — модель получает «память недоступна», хотя две словесные ветки работать могли.

Сделать вектор необязательным: смысловая часть отключается условием на `NULL`, словесные
ветки работают. Модели честно сообщать, что подбор неполный, — иначе она примет «не нашлось»
за «этого нет». Отказ эмбеддера обязан попадать в лог как ошибка: деградация не должна быть
тихой. Повторов к эмбеддеру внутри хода не добавлять.

#### Задача 18 — запись #189: расчистка пробки с частичной записью

Если разбор упал после того, как записал часть воспоминаний, дорожка встаёт и обе операторские
команды этот случай отвергают.

Лечить стоит двумя путями сразу: автоматически — голова в `failed`/`ambiguous`, у которой
наследник уже завершён, помечается пропущенной и курсор идёт по цепочке дальше; операторской
командой — на остальные случаи, где автоматика решить не может.

#### Задача 19 — запись #190: видно ли, что воркер индексации жив

Нет healthcheck, нет логов, метрика одинакова в работе и в простое. Пустой лог у этого
контейнера означает «ошибок не было», и отличить это от «процесс встал» нечем.

#### Задача 20 — запись #191: логи

71% строк боевых логов — служебные health-проверки, из-за чего история короче шести суток.
Отфильтровать служебные проверки, удлинить доступную глубину.

## 6. Чего делать нельзя

- **Не создавать `CLAUDE.md`** и не восстанавливать его хардлинком. Файл удалён намеренно
  (коммит `fe56336`), правила живут только в `AGENTS.md`. Если файл появился в рабочей копии —

- **Не открывать заново** записи #186, #187, #188, #211, #212.
- **Не сносить векторный индекс** — решение владельца обратное: довести до рабочего состояния.
- **Не добавлять реранкер** — не планируется.
- **Не менять боевую базу, не перезапускать боевые контейнеры, не собирать релиз вручную.**
  Чтение боевого окружения — можно и нужно, и чем больше замеров, тем лучше. Выкладка
  идёт через CI/CD по инструкции деплоя и отдельным шагом, не ночью и не между делом.
- **Сливать свои PR в `develop` — можно и нужно**, по одному на волну, после зелёного
  полного прогона. Это не требует отдельного согласования.
- **Не выносить поведение в `.env`.** Пороги, окна, лимиты, размеры кусков — в
  версионируемой конфигурации проекта или в коде. В `.env` только секреты и привязки к
  окружению.
- **Не придумывать значения по умолчанию** для отсутствующих обязательных данных. Падать
  сразу с понятной ошибкой.
- **Не добавлять скрытые повторы.** Повтор допустим только под подтверждённый временный сбой,
  ограниченный и наблюдаемый.
- **Не помещать `*.test.ts` в `agent/tools/` или `agent/channels/`** — Eve примет их за
  рабочие модули.
- **Не проверять формулировки промптов тестами на конкретные фразы.** Их проверяют чтением
  диффа и живым чатом; тестами проверяют количественный эффект.

#### Задача 5 — лучший кусок запроса вместо среднего (#194)

### Волна 3 — индекс и куски. Ветка `feat/memory-wave-3-index`

#### Задача 7 — векторный индекс (#201)

- Смысловая ветка переписана в форму «упорядочь по расстоянию, возьми n»: сначала ближайшие куски,

  по-прежнему предпочтёт прочитать всё — и правильно сделает; работа на вырост, как и сказано в

#### Волна 4 — независимое ревью и правки после него

Ревью диффа нашло восемь настоящих дефектов из десяти находок; все исправлены в `cf1eea5`.

**Ход опознавался неверно.** Eve нумерует ходы внутри сессии (`turn_0`, `turn_1`, …), а сессия
пересоздаётся каждые 50 завершённых ходов. Журнал ключевался парой «беседа + ход», поэтому после
ротации имена шли по второму кругу: номер хода переставал расти, окно `> N - 3` при N = 1 покрывало
весь журнал беседы и прятало из автоподборки всё, что ей когда-либо показывали. Ход теперь
опознаётся сессией Eve вместе с идентификатором.

**Служебная строка доходила до человека** тремя путями: промежуточное сообщение перед вызовом
инструмента шло мимо вырезания; регулярное выражение снимало только первое вхождение; вхождение
в середине строки не снималось вовсе. Она же ломала ответ-реакцию — текст переставал быть одной
директивой, и ход падал с `AGENT_TELEGRAM_REACTION_DIRECTIVE_INVALID`. Вырезание перенесено к
границе транспорта, до решения о виде ответа, и ведёт построчный разбор с отслеживанием блоков
кода; общая часть с aside-директивой вынесена в `markdown-code-fence.ts`.

**Счётчик был неидемпотентен:** он двигался до барьера повторной доставки, поэтому повторная
обработка хода считала запись дважды. Теперь отметка стоит в самом журнале (`used_at`), и счётчик
двигается один раз на показ.

Дополнительно: окно больше не включает текущий ход; делегированный субагент окна не получает;
журнал ограничен глубиной в 50 ходов беседы (боевой темп — около 360 ходов в сутки, по 12 строк на
ход, иначе журнал за месяцы перерос бы саму память); формула кривой собирается в одном месте для
SQL и TypeScript, `CASE` без `ELSE`, полноту видов проверяет тест против перечисления в базе;
фильтр окна и метрика `recentlyShown` читают один текст условия; индекс по `usage_count` убран.

Полный прогон в Docker после правок: 442 файла, 2859 тестов, зелёный.

### Волна 5 — наполнение памяти. Ветка `feat/memory-wave-5-writing`

#### Задача 13 — слот свойства (#205)

Миграция `111`: `attribute`, короткое имя свойства. Новая запись того же субъекта с тем же именем
переводит прежнюю в `superseded` и связывает их через `claim_relations` типом `temporal_update` —
механизм из `053` уже существовал, новый не заводился. Прежняя версия не удаляется: `list_memories`
с `history=true` показывает её со `status=superseded`, экспорт содержит всегда.

Замещение ограничено с четырёх сторон: семья, область памяти и её раздел, субъект во всех четырёх
формах, имя свойства. Сравнение читает сохранённую строку, а не повторяет её значения параметрами.
Против главного риска записи — слишком общего имени: сорок символов, нормализация как имени,
обратимость при отмене и при удалении, `supersededRefs` в ответе инструмента и `attribute` у каждой
показанной модели записи, чтобы она видела уже заведённые имена.

Нити прежней версии новой не наследуются: это отдельная запись со своим намерением, а не
переформулировка. Попутно: мягкое удаление снимает `superseded_by` — форма жизненного цикла
запрещает `retracted` на кого-то ссылаться, и без этого удаление замещённой записи упиралось бы в
ограничение базы.

#### Задача 14 — проверка соседей при записи (#208)

Замер боевой базы на 1030 активных записях не эпизодного вида: гейт при 0.90 остановил бы 360
записей со средним 3.8 соседа, при 0.92 — 164, при 0.93 — 100 с 1.3 соседями, при 0.94 — 48, при
0.95 — 33. Замер соседнего проекта: настоящие дубли ≈ 0.934, разные факты об одном человеке
0.916–0.924. Порог 0.93 лежит между полосами; выше — теряем дубли, ниже — каждая третья запись
упирается в отказ.

Код ничего не склеивает: порог решает только, показывать ли соседей. Пройти можно, перечислив
показанные memoryRef в `distinctFrom`; несписанный сосед останавливает запись снова, поэтому
объявление не может быть бланковым. Эпизод не проверяется, точный повтор по-прежнему подкрепляет
сам, недоступность сервиса эмбеддингов пропускает запись. Оба вектора считаются до открытия
транзакции.

#### Задача 15 — разбор видит, что уже записано (#204)

Два блока перед пакетом: записи этой беседы и хвост сообщений прошлого пакета, оба экранированы
как недоверенные. Инструкция получила третий исход: обновить существующую, задать тот же
`attribute`, либо сохранить отдельно.

Удорожание посчитано до внедрения: сообщение на бою 139 символов, пакет из пятидесяти с JSON
≈ 14 000 символов; запись 239 символов, пятнадцать записей ≈ 4 500, то есть треть сверху. При
≈ 237 пакетах в месяц это несколько сотен тысяч лишних токенов. Выборка — самые свежие записи
собственной области памяти, а не поиск: у пакета нет одного вопроса, а дубли живут в свежем.

#### Задача 16 — даты событий (#213)

Миграция `112`: необязательная `occurred_on` датой, не отметкой времени. `search_memories` принимает
`from` и `to`; отбор по дате события, у записей без неё — по дате появления. В этом режиме слова
запроса в отборе не участвуют. Старение осталось на дате появления, и это закреплено тестом.

### Волна 6 — эксплуатация. Ветка `feat/memory-wave-6-operations`

#### Задача 17 — поиск без сервиса эмбеддингов (#209)

Вектор запроса стал необязательным: пустой список проходит в запрос как есть, `unnest` по пустому
массиву не даёт строк, смысловая ветка не участвует, словесные работают. Нити активируются по
найденным записям и подсказкам навыков, без близости названий.

Модель узнаёт о неполноте: предупреждение в блоке памяти и `incompleteSelection` в ответе
`search_memories`. Отказ пишется ошибкой `AGENT_MEMORY_SEMANTIC_BRANCH_UNAVAILABLE`. Повтора к
сервису внутри хода нет — он и так плохо себя чувствует.

#### Задача 18 — расчистка пробки с частичной записью (#189)

Команда `skip-partial ID ПРИЧИНА`: пакет помечается пропущенным, курсор идёт дальше, записанное
остаётся. Исход выбран по рекомендации самой записи — вариант 1. Откат записанного потребовал бы
механизма отмены записи разбора, которого нет; разбор вручную кладёт переписку перед оператором.
Решение, причина и число оставленных воспоминаний идут в аудит.

Автоматическая половина из плана не делалась: описанное состояние («голова в failed, у которой
наследник завершён») по коду недостижимо — дорожка выдаёт пакет только когда `predecessor_sequence`
равен курсору. Писать автоматику под непоказанное состояние и отдавать ей судьбу уже записанных
воспоминаний — не то, чего просит запись.

#### Задача 19 — видно ли, что воркер индексации жив (#190)

Все три пункта записи. Отметка готовности на каждом проходе цикла плюс healthcheck; стартовая
строка в лог; миграция `113` с возрастом самой старой ожидающей задачи и тревога
`OsinaraMemoryIndexingStalled` на десять минут. Пульс в лог не добавлялся — это задача healthcheck.

#### Задача 20 — логи (#191)

Nginx не пишет успешные проверки живости (условный журнал по статусу), неуспешные пишутся.
У cli-proxy-api журнал ведёт сторонний бинарник, поэтому опрос разрежен с пяти секунд до тридцати
со `start_interval` на время подъёма. Вместе это около двух третей недельного объёма: 151 167 и
100 194 строки из 355 135. Пункт 3 записи — перепроверить глубину хранения через неделю — остаётся
за владельцем: правило отсечения истории живёт вне репозитория.
